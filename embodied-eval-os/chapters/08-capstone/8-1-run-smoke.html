跑通 smoke，读一条 trace

前面七部分都在讲架构、契约、纪律。现在该把手弄脏了。这一节我们只做一件极小的事：在你自己的机器上跑通 examples/run_smoke.py，让它从零造出一条 EpisodeTrace，然后打开那个 JSON 文件，亲眼确认——这本书反复强调的"证据"，长什么样、字段在哪、claim boundary 写在哪一行。这是把整本书"落地"的第一步：一条真实的、可审计的证据 artifact。

smoke 是什么，不是什么

EOS 有两条评测路径。一条是 provider 驱动的 live evidence-chain loop（RPF-10 / EVL，我们在 6.2 看过它的八动词时序）；另一条是极简的 in-process 路径，由 EpisodeRunner 驱动。run_smoke.py 走的是后者。它不连任何真实仿真器，用的是一个纯 Python 的 SemanticProxyBackend——没有 PhysX、没有 MuJoCo、没有渲染。它存在的唯一意义，是用最少的依赖,把"造一条合法 trace"这条主干跑通一遍。

正因为如此，它也是 8.3 里 PR 前必跑的第一条命令：如果连 smoke 都跑不通，说明 trace 的骨架本身坏了，后面什么 live lane 都不用谈。

运行时依赖只有两个

别担心装一堆仿真器。EOS 的 pyproject.toml 里运行时依赖只有 pyyaml 和 typing-extensions——所有 sim 引擎都是 adapter 侧的可选依赖。smoke 用的 SemanticProxyBackend 是零外部依赖的纯 Python，所以它在任何装了 Python 3.10+ 的环境里都能跑。

逐行读 run_smoke.py

整个脚本不到六十行，骨架就是 EOS 评测路径 A 的最小调用序列：建 spec → 装 runner → run → evaluate → 存档。先看怎么声明被评测的世界。

examples/run_smoke.py
scene = SceneSpec(
    scene_id="dummy_scene",
    asset_instances=[AssetInstance(instance_id="obj", asset_id="dummy_object")],
)
task = TaskSpec(
    task_id="smoke.move_to_threshold",
    scenario_pack="smoke",
    scene_id="dummy_scene",
    instructions=["Move the dummy object to position >= 1.0."],
    success_conditions=["semantic_proxy_object.position >= 1.0"],
)

SceneSpec 和 TaskSpec 都是 core 里 domain-agnostic 的契约（我们在 1.1 见过它们）。注意 scenario_pack="smoke"：哪怕是这个玩具任务，也老老实实声明了自己属于哪个 pack——因为这个字段最终会被原样写进 trace，成为 provenance 的一部分。success_conditions 是一句声明式的成功判据，等会儿 evaluator 会照它判分。

接下来把 backend、model、spec 装进 EpisodeRunner 并 run。这是整条路径的心脏：

examples/run_smoke.py
runner = EpisodeRunner(
    backend=SemanticProxyBackend(),
    model=RandomPolicyAdapter(delta=0.4),
    task_spec=task,
    scene_spec=scene,
    max_steps=10,
)
trace = runner.run(seed=42)
result = TaskOutcomeEvaluator().evaluate_episode(trace)
trace.episode_metrics.update(result.summary)

每个零件都是一个可替换的契约实现：

  • SemanticProxyBackend 满足 EpisodeBackend 协议——它提供 load_scene / reset / step / measure / project_physical_state。这里它做的"物理"只是一个语义代理：把一个标量 position 往阈值推。
  • RandomPolicyAdapter(delta=0.4) 满足 EpisodeModel 协议（reset / act）。它的 act() 永远返回 {"delta": 0.4}——是全书最朴素的"策略"，但形状是真的（我们在 8.2 会照着它写自己的 adapter）。
  • run(seed=42) 跑最多 10 步，产出一条 EpisodeTrace。
  • TaskOutcomeEvaluator 拿这条 trace 算 task_outcome family 的指标，回填进 episode_metrics。

这里有一个容易被忽略、却是 EOS 招牌的细节：EpisodeRunner 会把 STANDARD_BACKEND_COMPONENTS——platform / physics / renderer / sensors / control / process_runtime 六个组件——强制写进每一条 trace。哪怕你的 backend 是个玩具，它也得交代清楚这六格各是什么。这就是铁律三在代码里的落点：没有"一个 backend 就叫 Isaac"这种含糊。

真的跑一下

最简单的形式，不写任何 trace 文件，只在终端打印摘要：

terminal
python examples/run_smoke.py

你会看到三行输出：episode_id=...、steps=10、metrics={...}。要真正读 trace，加上 --trace-dir，让它把 JSON 落盘：

terminal
python examples/run_smoke.py --trace-dir /tmp/eos_smoke
# 末行会打印 trace_path=/tmp/eos_smoke/<episode_id>.json

落盘是靠 TraceStore(args.trace_dir).save_json(trace) 完成的——TraceStore 是 core 的 recorder，负责把 trace 序列化成寻址稳定的 JSON。

在 DSW / CPFS 上：用 $EEOS_PYTHON

共享开发环境里系统 python 未必是对的解释器。项目约定用 $EEOS_PYTHON（指向 .../envs/embodied-eval-os-py310/bin/python）跑所有命令，例如 $EEOS_PYTHON examples/run_smoke.py。这一点在 8.3 讲 PR 前置命令时还会再提一次。

从 EBench 看 你第一次"跑通"是 gmp submit，这次是一条本地 smoke

在 EBench 里，你第一次让模型动起来，多半是往 GenManip server 发一个 gmp submit，等一个远端 rollout 回来，最后拿到一个 success 数。那是 client–server 黑盒：你看到的是结论，看不到中间的证据骨架。这里的 smoke 反过来——它在你本地一次跑完，产物不是一个分数，而是一条完整的证据 artifact。你能打开它、逐字段读它。EOS 把重量从"拿到一个数"挪到了"拿到一条能审计的 trace"，这一节就是第一次亲手验证这个转变。

打开 JSON，找证据

现在 cat 那个 trace 文件（或在编辑器里打开）。它就是 3.3 里 EpisodeTrace dataclass 序列化的样子。把目光放在三处——它们是这条 trace 之所以是"强证据"而非"一个裸数字"的原因：

/tmp/eos_smoke/<episode_id>.json（示意结构）
{
  "episode_id": "...",
  "task_id": "smoke.move_to_threshold",
  "scenario_pack": "smoke",
  "backend_profile_id": "...",
  "seed": 42,
  "model_profile_id": "random_policy",
  "versions": { "repo_commit": "...", "task_spec": "...", "...": "..." },
  "backend_components": {
    "platform": "...", "physics": "...", "renderer": "...",
    "sensors": "...", "control": "...", "process_runtime": "..."
  },
  "privileged_state_policy": "model_input_excludes_privileged_state",
  "claim_boundary": "Trace evidence only; no simulator fidelity or real-world safety claim.",
  "steps": [ { "step_index": 0, "...": "..." } ],
  "episode_metrics": { "...": "..." }
}
  1. 六个 backend_components：哪怕是 SemanticProxy，它也把 platform/physics/renderer/sensors/control/process_runtime 六格填齐了。这是你日后做跨后端对比的根基——没有这六格，你根本说不清"换了哪个组件"。
  2. claim_boundary：默认值就写死在那里——"Trace evidence only; no simulator fidelity or real-world safety claim." 这条 smoke 用的是语义代理，它不声称仿真保真，更不声称真实世界安全。这行字是 EOS 诚实的物理体现。
  3. versions：repo commit、task spec version、seed、determinism 相关信息都在这里。3.3 说过一句狠话——"Without this metadata, the trace is not considered valid evidence."（没有这些元数据，这条 trace 就不算有效证据。）一条没有 provenance 的 trace，等于没有 trace。

顺带留意 privileged_state_policy 默认是 model_input_excludes_privileged_state：模型看到的输入不含特权状态，这正是 privileged state rule 的默认姿态。RandomPolicy 只看到脱敏后的 observation，evaluator 才看得到全貌。

这条 smoke 证明了什么 / 不证明什么

证明：EOS 的 trace 主干能在零仿真依赖下从头跑通，产出一条字段齐全、provenance 完整、claim boundary 显式的 EpisodeTrace；评测路径 A 的 build spec → run → evaluate → save 链路是通的。
不证明：任何关于仿真保真、物理正确、跨后端等价或真实世界安全的东西。SemanticProxyBackend 是一个 semantic proxy，不是 real physics；它的 task_outcome 只对这个玩具阈值有意义。"跑通了 smoke"是contract closure（证据链存在），不是 outcome closure（某个真实结果成立）。把这两者分清，是整本书教你的第一直觉。

这一节带走的

你刚刚亲手造了一条证据，并读懂了它为什么是证据：六个 backend 组件交代了"在哪台机器上、用什么物理/渲染跑的"，versions 钉死了"在哪个 commit、哪个 seed 下复现"，claim_boundary 老实写明"这只能证明 trace 层面的东西"。一条 trace 之所以可信，不是因为它给了你一个数，而是因为它把这些边界全都摊开在 JSON 里。
