PR 纪律：让项目对自己诚实

整本书讲的"证据""claim boundary""不污染 core"，听起来都很高尚。但高尚的原则如果只活在文档里，迟早会被一个赶 deadline 的 PR 悄悄破坏。EOS 的最后一课，是它怎么把这些原则固化成机器会执行的纪律：几条 PR 前必跑的命令、几道 make gate、一条 Record Rule、一份 claim boundary 模板。这一节是全书的文化收束——正是这套纪律，让前面所有的"证据"配得上被信任。

三条必跑命令

任何非平凡 PR 之前，三条命令必须绿：

terminal
python examples/run_smoke.py          # trace 主干还跑得通吗
pytest -q                             # 单元/集成测试
python scripts/check_core_leakage.py  # core 里有没有混进领域名/sim 名

三条各守一个底线，缺一不可：

  • run_smoke.py——确认评测路径 A 的 build spec → run → evaluate → save 没坏（就是你在 8.1 跑的那条）。
  • pytest -q——常规测试网，包括那些守着 trace 不变量、State V2 拒绝 legacy key、repo-commit 取自所属 repo 而非 CWD 的测试。
  • check_core_leakage.py——扫 core/**/*.py，禁止出现 ebench / genmanip / mujoco / pipette / centrifuge / qpos / qvel 这类 token。这是铁律一从"约定"变成"CI 红灯"的那一步：它比文档 CLAUDE.md 的短表更严，词边界匹配，出现一个就 fail。
DSW / CPFS：用 $EEOS_PYTHON

在共享环境里把上面三条的 python 换成 $EEOS_PYTHON（指向 .../envs/embodied-eval-os-py310/bin/python），否则可能跑到错误的解释器。如果某条命令在你的环境里确实不可用，PR 纪律要求你在 PR 里写清原因——而不是默默跳过。

分层的 make gate

三条命令只是最快的那一层。真正的关卡是一组分层 gate，越往后越严，对应 release claim levels 越往宽走：

  • make check / check-local——快速 commit gate：smoke + 非 scenario 的 pytest + leakage + state-v2 迁移检查 + profile 检查 + diff 检查。日常提交跑这个。
  • make check-pr——开 PR 前的更宽一层。
  • make check-merge——合并前。
  • make release-live-gate / release-live-sdk-gate——发布级。这一层才碰 live SDK lane，由 check_required_live_lanes.py、check_architecture_debt.py 之类强制 no-silent-fallback：缺测量就得显式记 blocked_*，绝不许填 0 或 success=true 蒙混过去。

这套阶梯的意义是：你日常迭代不必跑全套，但没有任何路径能绕过 gate 直接声称发布级结论。叙事里"由窄到宽不许跳级"的纪律，在 Makefile 里有物理对应。

Record Rule：给每个决定留痕

非平凡改动，除了过 gate，还要留一份带日期的记录，放在 docs/records/YYYY-MM-DD-short-title.md。模板是固定的六段：

docs/records/2026-06-13-my-change.md
# 2026-06-13 Short Title

## Context            ── 为什么要改
## Decision / Change  ── 改了什么、为什么这样改
## Files touched      ── 动了哪些文件
## Validation         ── 跑了哪些命令、结果如何
## Known limitations  ── 这次没解决/不声称的东西
## Next actions       ── 后续要做什么

这不是为了好看。整本书的 硬仗时间线——trace/evidence spine、AutoBio 的 faithful_reproduction_not_approved、stage50 的 qpos 重映射 bug、WR/judgeable loop 的 first-divergence 账本——之所以能被你今天读到、能被追溯"当时为什么这么决定"，全靠这一条条 record。Known limitations 那一段尤其重要：它逼着每个改动作者，亲手写下"我这次没证明什么"。

从评测科学 看 Record 与 claim 模板，就是机构化的 model card

评测科学里有一套对抗"过度宣称"的制度工具：Model Cards（Mitchell 等，FAT* 2019）要求模型附上"适用范围 / 不适用范围 / 已知局限"；Datasheets for Datasets（Gebru 等，CACM 2021）要求数据集附上来源与动机；NeurIPS 的 reproducibility checklist（Pineau 等，JMLR 2021）逼作者交代 seed、显著性、算力。EOS 的 Record Rule + PR claim 模板，本质就是把这些"institutional honesty"机制搬进了一个评测 OS 的工程流程里——每条 trace 有 provenance，每个改动有 known limitations，每个 PR 有"proves / does not prove"。诚实不再依赖个人自觉，而是被流程强制。

PR 模板里的两道诚实检查

PR 模板本身带两段不能空着的检查，它们是这套文化最锋利的部分：

  • Core boundary check——你这次有没有往 core 里加领域名/导入？（呼应 leakage 脚本，但要你用人话再确认一遍 placement：该进 pack 的进了 pack，该进 adapter 的进了 adapter。）
  • Claim boundary——分两栏写明：What this PR proves / What this PR does not prove。这就是全书那个琥珀色方框，在 PR 流程里的强制版。
这一节（和这本书）真正证明了什么

把整本书收束成一句：EOS 的护城河不是它支持多少个仿真器，而是它对自己有多诚实。check_core_leakage.py 让"不污染 core"成为红灯；分层 make gate 让"不跳级声称"成为关卡；Record Rule 让每个决定都带着 Known limitations 留痕；PR 模板的 "proves / does not prove" 让每次合并都得先划清边界。
这套纪律不能替你证明你的模型很强、你的物理很准、你复现了某个官方 benchmark——它从不声称这些。它能做的，是让别人有理由相信你 trace 里的每一个数。前面七部分讲的所有"证据"，正是被这一节的纪律撑起来的：没有它，trace 只是好看的 JSON；有了它，trace 才是可审计的证据。这就是这本书想留给你的最后一个直觉。

这一节带走的

三条必跑命令（smoke / pytest / leakage）守底线，分层 make gate 守 claim 级别，Record Rule 给每个决定留痕（尤其 Known limitations），PR 模板的 Core boundary check 与 "proves / does not prove" 把诚实写进每次合并。这套东西合起来，就是 EOS 把"claim boundary"从一句口号变成一条工程流水线的方式。
