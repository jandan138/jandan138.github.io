适配器即防腐层：EBench / AutoBio

scenario pack 接的是你自己设计的场景。但具身评测的现实是：外面已经有一堆做好的 benchmark，各自带着自己的 runtime、score schema、相机名、动作维度。要把它们接进来，又不让它们的设计反向"塑形" EOS 的 core——这正是 adapter 要解决的问题。它的形态有个经典名字：anti-corruption layer（防腐层）。

为什么是"防腐层"

防腐层是一个边界模式：当你的干净领域模型要和一个外部的、你无法控制的系统打交道时，你不让外部系统的概念漏进来，而是在中间放一层翻译，把外部世界的语言翻成你自己的语言。铁律二把这条写死了：EBench、GenManip、AutoBio、Isaac 4.1 只能经 adapter 接入，不得反塑 core API。

具体到代码红线——这些是允许的：

允许
adapters/ebench/
adapters/autobio/
configs/backend_profiles/ebench_genmanip_legacy.yaml

而这些是不允许的——它们会把外部 benchmark 的概念焊进 core：

不允许
core.GenManipRuntime
core.Lift2Action
core.EBenchScore
从 EBench 看 你的"家"被收编成了一层翻译

EBench 在 EOS 里的定位是 a compatibility target and design reference, not the base framework——一个兼容目标和设计参考，而不是底座。这听起来有点冷酷，但它正是 0.1 那句"EBench 现在是一个 adapter"的工程落地。你熟悉的那套 client–server、capability profile、action chunking 不会消失；它们会被提取成思想吸收进 core，而把具体实现关进 adapters/ebench/。

EBench adapter：吸收什么 vs 留下什么

设计一个防腐层，最关键的判断是哪些东西值得提炼成通用概念（吸收进 core），哪些是 benchmark 的偶然实现细节（必须留在 adapter）。EBench 这条线分得很清楚：

EBench adapter 边界
吸收进 core（变成通用契约）：
  multi-axis capability profile      # 多轴画像哲学
  client–server model interface      # 模型与环境解耦
  action chunking                    # 动作分块
  train / test / generalization split
  diagnostic report                  # 诊断式报告
  依赖隔离

留在 adapter（外部偶然实现）：
  GenManip runtime                   # 具体仿真 server
  Isaac Sim 4.1 lock-in              # 版本锁定
  Lift2 embodiment                   # 具体本体
  EBench score schema                # 它的打分格式
  dataset layout / server·client 命令
  camera names / action dims         # 相机名、动作维度

翻译的产物是一张映射表：外部世界的每个概念被翻成 EOS 的一个契约对象。

EBench → EOS 映射
EBench task        → imported TaskSpec
GenManip runtime   → adapter runtime config
Lift2 embodiment   → 一个 EmbodimentSpec
EBench score       → MetricResult
Isaac Sim 4.1      → legacy BackendProfile (ebench_genmanip_legacy.yaml,
                                            purpose: compatibility_only)

对应的代码就住在 adapters/ebench/：import_task.py、map_score.py、runtime_probe.py、fixture_trace.py、smoke_*.py。

smoke 的目标：是翻译通路，不是复现

这里有一个极易被夸大的地方。EBench adapter 的 smoke 目标只是证明一条翻译通路是通的：

EBench adapter smoke 目标
EBench / GenManip episode
   → EBenchAdapter
   → EpisodeTrace
   → MetricResult
   → Report stub

注意终点是一个 Report stub，不是一张和官方对齐的成绩单。这条 smoke 不是 full reproduction——它不声称复现了 EBench 的官方 benchmark 数字，只声称"外部 episode 能被翻译成一条带证据的 EpisodeTrace 并跑过一遍度量"。

compatibility smoke ≠ benchmark reproduction

一条 adapter smoke 跑通，证明的是翻译契约成立：外部 benchmark 的 task/score 能被映射进 EOS 的 trace 与 metric 体系。它不证明：你复现了那个 benchmark 的官方结果、你的后端和它的后端物理等价、或者模型在那个 benchmark 上的真实排名。"compatibility smoke" 和 "full benchmark reproduction" 是必须分开声明的两件事。

AutoBio adapter：一个 MuJoCo 数字生物实验室

第二个 adapter 是 AutoBio——一个跑在 MuJoCo 上的数字生物实验室 benchmark（arXiv:2505.14030，HKU/TeleAI/Tsinghua/SJTU）。它有 16 个任务、三档难度，并且为了表达实验室操作写了不少自定义 MuJoCo 插件：螺纹用 SDF of a circular helix（圆螺旋的符号距离场）而不是 mesh 碰撞来表达、还有 detent、eccentric、quasi-static liquid；机器人涵盖 UR5e/ALOHA/Robotiq/DexHand；资产经 PGSR 3D Gaussian Splatting → CAD → watertight MJCF 流水线生成。

对这样一个"高保真但和我们栈不一样"的 benchmark，EOS 给了两种复现模式，而且把它们的 claim 边界划得很清：

  • faithful（忠实）——经 adapters/autobio/ + configs/backend_profiles/mujoco_autobio.yaml，目标是真的去对接 AutoBio 的 MuJoCo runtime。
  • semantic（语义）——经 scenario_packs/scientific_lab/，用 EOS 自己的语义 proxy 原语重新表达 AutoBio 风格的任务（pipette、拧盖……）。

runtime_probe：一个就绪探针，不是一次运行

那 faithful 模式现在跑起来了吗？去读 adapters/autobio/runtime_probe.py 你会看到一个很诚实的答案：它产出的不是一次 run，而是一份READINESS probe（就绪探针）。它检查 AutoBio 根目录在不在、几个关键文件（pickup_centrifuge_tube.py、libmjlab.so.3.3.0……）和 Python 依赖（mujoco、jax、trimesh……）齐不齐——然后老老实实写下：

embodied_eval_os_autobio_runtime_probe.v0（节选）
"runtime_mode": "readiness_probe",
"runtime_status": "not_executed",
"runtime_attempted": false,
"backend_components": {
  "physics":         {"name": "mujoco", "status": "not_started"},
  "process_runtime": {"name": "autobio_task_systems_and_plugins",
                      "status": "not_started"}, ... },
"claim_boundary": "AutoBio readiness evidence only. This probe does not
   execute MuJoCo, does not load an AutoBio task, and does not support
   official AutoBio benchmark reproduction ..."

每个 backend component 都标 not_started，runtime_attempted=false。这就是一个 compatibility smoke 的诚实形态：它不假装跑过 MuJoCo，它只回答"如果要跑，环境齐不齐"。注意它还遵循 No Silent Fallback——环境不齐时 status 是 skipped，绝不悄悄填一个"成功"。

从物理后端 看 为什么 semantic 模式不能声称物理等价

AutoBio 的螺纹是一段真实的 SDF-of-a-helix 在 MuJoCo 软接触求解器里跑出来的接触力。而 scientific_lab 的 semantic 模式（下一节细看）是用 proxy 原语返回一个语义 dict——它根本没有跑那个螺纹求解器。同一个"拧盖成功"，一边来自接触动力学，一边来自一个语义判据。这两者可以都有用，但它们不是同一种证据。

adapter 的共享契约：validate_runtime_trace

所有 adapter 共用一道闸：adapters/runtime_contract.py::validate_runtime_trace(...)。它强制 adapter 产出的 trace 满足几条外部 provenance纪律：在 episode_metrics 和 metadata 里双写 runtime_status/runtime_attempted、必须带 claim_boundary、并且外部仓库的 commit 要一致（metadata.external_commit == versions.external_commit），合法的 runtime_status 只有 {"executed", "skipped"}。

这道闸的意义是：一条来自外部 benchmark 的 trace，必须随身携带"它来自哪个外部 commit、跑了还是跳过、它声称/不声称什么"。没有这套 provenance，外部证据就不能进 EOS 的证据账本。

semantic reproduction ≠ 与 AutoBio 插件物理等价

用 scientific_lab 的 semantic 模式重新表达 AutoBio 风格任务，证明的是这些任务的语义可以在 EOS 的层里被表达和评测。它不证明：你复现了 AutoBio 的官方结果，也不证明你的 proxy 原语与 AutoBio 的自定义 MuJoCo 插件（SDF 螺纹、quasi-static liquid）物理等价。EOS 的记录里，AutoBio 的 faithful reproduction 状态被明确判为 faithful_reproduction_not_approved——roadmap 走完也不等于忠实复现。

这一节带走的

三点：（1）adapter 是 anti-corruption layer——外部 benchmark 只能经它接入，不得反塑 core；它吸收思想（多轴 profile、client–server、action chunking、split），留下偶然实现（GenManip runtime、Isaac 4.1、Lift2、score schema、相机名、动作维度）。（2）EBench smoke 的终点是 EpisodeTrace → MetricResult → Report stub，是 compatibility smoke 而非 full reproduction。（3）AutoBio 的 runtime_probe.py 产出的是 runtime_status=not_executed 的就绪探针；validate_runtime_trace 用外部 provenance 把所有 adapter trace 卡在统一契约上。
