Scenario pack contract：场景如何接进一台评测 OS

前三部分你都在看 core——那层场景中立的契约骨架。但 core 自己不评测任何东西：它不知道什么是 pipette、什么是 hazard level、装配对位算不算成功。这些语义住在 scenario pack 里。这一节回答一个很具体的问题：一个 pack 到底要交出哪些东西，才算"接进了" EOS？而当你去仓库里找那个叫 ScenarioPack 的基类时，你会发现——它根本不存在。这恰恰是设计的关键。

一个 pack 提供什么

回忆 0.1 的那张非目标清单：scientific-lab、wet-lab safety、home manipulation、factory assembly、field robotics 全都不是 core，而是 scenario pack。所以一个 pack 的职责，就是把"某个具身领域的全部语义"打包成一组 core 能消费的产物，而不去碰 core 抽象本身。具体它要交出：

  • tasks——一组 TaskSpec（指令模板、初始状态分布、成功/失败条件）。
  • scenes——场景布置（SceneSpec），定义有哪些物体、容器、设备。
  • assets——一份 asset_manifest.yaml，列出几何/材质资产及其 provenance。
  • embodiment maps——把后端的物理量映射到场景语义组件的 semantic_component_map.yaml。
  • metrics——一组 MetricSpec 实例（注意：core 只定义 metric family，pack 负责实例化具体度量）。
  • process primitives——把 backend-normalized 的物理投影翻译成场景语义状态的代码（本节主角）。

换句话说：pack 是"领域知识"，core 是"评测骨架"。骨架不变，领域知识可插拔——这正是"OS"那个词的含义。

从 EBench 看 你已经见过一个 pack 了

EBench 里 home-manipulation 那套任务（把蛋挞放进微波炉、关抽屉……）在 EOS 里就是 scenario_packs/home_manipulation/——一个 EBench-compatible 的 pack。你在 EBench 里写过的"任务定义 + 场景 + 成功判据"，本质上就是在写一个 pack 的内容，只是当时它和 Isaac、Lift2 焊死了。EOS 做的事，是把这套结构从某个具体仿真器里拔出来，变成一份可移植的契约。

必需的目录结构

contract 文档对一个 pack 的目录布局有明确要求。一个完整的 pack 大致长这样：

scenario_packs/<pack_name>/
README.md
tasks/<id>.yaml                          # TaskSpec
scenes/<id>.yaml                         # SceneSpec
assets/asset_manifest.yaml              # 资产清单 + provenance
embodiment_maps/semantic_component_map.yaml
metrics/metric_spec.yaml                # MetricSpec 实例
process_primitives/README.md            # 过程原语（代码在同目录）
samplers/sampler_spec.yaml              # 初始状态采样
baselines/baseline_profiles.yaml
records/                                # 该 pack 的 dated records

这不是官僚主义。每个目录都对应 trace 里一个会被审计的字段：没有 asset_manifest 就没有 asset manifest version，trace 就缺一段 provenance；没有 metric_spec，报告里的数值就没有 family、单位、target direction 可对照。目录结构是证据结构的影子。

代码现实：没有 ScenarioPack 基类

现在讲最容易踩空的一点。如果你按直觉去 grep 一个 class ScenarioPack(ABC)，你会扑空——仓库里没有任何抽象 ScenarioPack 基类。EOS 故意不用"继承一个大基类"的方式定义 pack。一个 pack 的契约，是靠下面三件事组合实现的：

  1. subclass core 的三个原语 ABC。core 在 core/primitives/base.py 里只给了三个抽象类，每个都只要求实现一个方法 update(physical_state) -> dict：
src/embodied_eval_os/core/primitives/base.py
class InteractionPrimitive(ABC):
    """接触/交互语义：门铰链、螺纹盖、插拔、对位、地形接触……"""
    primitive_id: str
    @abstractmethod
    def update(self, physical_state: PhysicalStateProjection) -> dict[str, Any]: ...

class ProcessPrimitive(ABC):
    """过程/材料/任务动力学：材料转移 proxy、装配状态、传送带过程……"""
    primitive_id: str
    @abstractmethod
    def update(self, physical_state: PhysicalStateProjection) -> dict[str, Any]: ...

class DevicePrimitive(ABC):
    """仪器/家电/工厂设备的状态机。"""
    primitive_id: str
    @abstractmethod
    def update(self, physical_state: PhysicalStateProjection) -> dict[str, Any]: ...

注意这三个类的 docstring 里举的例子横跨家居、工厂、地形——它们是场景中立的。core 只承诺一件事：给你一个 backend-normalized 的 PhysicalStateProjection（L4，那个有 robots/objects/joints/contacts 的物理投影），你的原语把它翻译成你的领域语义，返回一个 dict。这个 dict 最终落进 TaskSemanticState（L5）。

  1. 用 spec dataclass 描述任务与度量——TaskSpec、SceneSpec、MetricSpec 等都是 core 的 frozen dataclass，pack 只是实例化它们，不继承、不改字段。
  2. 用自由的 builder 函数把场景拼起来。例如视觉 pack scenario_packs/visual_manipulation_micro/ 里就是 build_visual_push_slide_scenario(...) 这样的普通函数 + evaluate_progress(...)，没有任何"框架钩子"。

再加上一道外部约束：scripts/check_core_leakage.py 会扫描 core/**/*.py，一旦发现 pipette/contamination/mujoco 这类禁词就让 CI 失败——这保证了所有领域语义只能住在 pack 侧。三个 ABC + spec dataclass + builder 函数 + leakage checker，合起来就是"pack contract"。没有第五样东西，也没有 widget。

为什么不要一个大基类

一个 ScenarioPack 抽象基类听起来很整洁，但它会变成一块"中心化的领域知识吸铁石"：每个新场景都想往基类上加一个方法、一个字段，最后 core 又被领域语义污染了——正是 1.4 那条红线要防的事。用"几个最小 ABC + 自由函数"代替大基类，让 core 暴露的契约面尽可能窄，领域代码反而获得最大自由。

TaskSpec 的必填字段

一个 pack 的入口是它的任务。TaskSpec 这个 dataclass 要求填齐以下字段，缺一不可：

TaskSpec（core 契约，pack 负责实例化）
task_id                       # 全局唯一
scenario_pack                 # 属于哪个 pack
instruction_templates         # 自然语言指令模板（喂给模型）
initial_state_distribution    # 初始状态怎么采样
observation_spec              # ObservationSpec：模型看得到什么
action_spec                   # ActionSpec：动作接口
success_conditions            # 什么算成功
failure_conditions            # 什么算失败
metric_specs                  # 这个任务用哪些 MetricSpec
allowed_backend_profiles      # 允许在哪些后端 profile 上跑
privileged_state_policy: evaluator_only

最后一行尤其要划重点：privileged_state_policy: evaluator_only。它把 3.3 讲过的 Privileged State Rule 钉死在任务定义这一层——这个任务的特权状态默认只给 evaluator/recorder 看，不喂给被测模型。一个 pack 即使写得再丰富，只要漏了这条策略声明，它产出的结果在证据意义上就是可疑的。

一个 pack "接进了" EOS，证明了什么

当一个 pack 提供了齐全的目录、合法的 TaskSpec、subclass 了三个原语 ABC，并通过了 leakage checker——它证明的是：这个领域的语义可以被 core 的契约表达、被 trace 审计、且没有污染 core。它不证明：这些任务在任何真实后端上跑通了、度量数值是真实物理、或者模型在这个领域有能力。"契约闭合"（contract closure）和"结果闭合"（outcome closure）是两件事——pack contract 管的是前者。

这一节带走的

三点：（1）pack = 领域语义的打包（tasks/scenes/assets/embodiment maps/metrics/process primitives），core = 不变的评测骨架；（2）pack contract 不靠继承一个基类，而靠 subclass core.primitives 三个 ABC（各实现 update(physical_state)->dict）+ 实例化 spec dataclass + 自由 builder 函数 + leakage checker 四者组合；（3）TaskSpec 必填字段里，privileged_state_policy: evaluator_only 把特权状态纪律钉在任务层。
