从一个 benchmark 到一台 evaluation OS

你刚刚合上 EBench 那本书。手里握着一个很具体的东西：一个跑在 Isaac Sim 上的 mobile-manipulation benchmark，一套 client–server 评测引擎，一张 capability profile。这本书要带你往上走一层——去看一个更贪心的问题：如果你不再满足于"再做一个 benchmark"，而是想造一台能评测任意场景、任意本体、任意物理与渲染后端的机器，架构会逼着你做出哪些选择？

你已经有了什么

先盘点一下你从 EBench 带过来的"家当"，因为这本书几乎每一节都会从这里出发：

  • 你知道 VLA 是怎么回事——拿一个 VLM backbone，接上输出 robot action 的能力；你甚至理解了 flow matching 怎么让策略表达多模态连续动作。
  • 你知道仿真栈：Isaac Sim = USD + PhysX + RTX，外加 cuRobo 做运动规划、GenManip 把仿真做成黑盒 server、LeRobot 管数据格式。
  • 你知道 benchmark 方法论：把单一 success rate 摊成多轴 capability profile，用 tracks × splits 守住训练/测试隔离。
  • 你知道评测引擎为什么是 client–server：把仿真当黑盒，让模型和环境的依赖互不污染。

这些都还在。区别是：在 EBench 里，这些东西长在一起——Isaac、Lift2 本体、GenManip server、那套 action 维度，是焊死的。换一个实验室场景、换一个物理引擎、换一种本体，你就得重写一遍。EOS 的出发点，正是这种"焊死"带来的痛。

一个 benchmark 不够

设想你现在要评测的不只是"把蛋挞放进微波炉"，还有：湿实验室里机器人会不会做出危险动作、工厂装配线上的对位精度、野外机器人会不会翻车、以及——最关键的——一个world model 能不能预测这些事情在发生之前就发生。再设想这些任务要分别跑在 Isaac、MuJoCo、Genesis 上，用不同的渲染器，喂给 actor、planner、safety-critic 等不同家族的模型。

这时候"再写一个 benchmark"就崩了。你需要的是一套契约：让场景、后端、模型、度量都能各自替换，而评测的骨架不变。这正是 EmbodiedEval OS 想做的事——它的官方定位就一句话：

“A domain-agnostic, backend-composable evaluation OS for embodied intelligence.”

注意"OS"这个词不是修辞。操作系统的本事是：定义稳定的接口，让上面的应用和下面的硬件都可以换。EOS 想成为评测领域的那一层——它定义 contracts，而把"实验室""Isaac""某个 VLA"都变成可插拔的 scenario pack 或 adapter。

从 EBench 看 EBench 现在是一个 adapter

这是全书最该先记住的一句话：你刚学完的整个 EBench，在 EOS 里被收进 adapters/ebench/ 和 scenario_packs/home_manipulation/。GenManip runtime、Isaac 4.1 lock-in、Lift2 本体、那套 action 维度——全部留在 adapter 里，不许反向塑造 EOS 的核心 API。EOS 从 EBench 吸收的是思想（多轴 capability profile、client–server 接口、action chunking、train/test split、诊断报告），而不是它的具体实现。

EOS 不是什么

一个项目的身份，往往是被它拒绝成为什么定义的。EOS 的设计文档第一页就摆出一张"非目标"清单，语气相当强硬。它不是：

  • an EBench fork；
  • a GenManip wrapper；
  • an Isaac-only benchmark；
  • a scientific-lab-only benchmark；
  • a VLA-only evaluation harness。

Scientific-lab、wet-lab safety、home manipulation、factory assembly、field robotics、warehouse logistics、real robots——这些统统是 scenario packs 或 adapters，而不是核心。这条原则会在 1.4 变成一条可执行的红线：一个叫 check_core_leakage.py 的脚本，会扫描核心代码里有没有出现 Pipette、GenManip、mujoco 这类名字，出现一个就让 CI 失败。

五条能力轴

EBench 教你"别只看一个数，要看多轴画像"。EOS 把这条原则推到具身智能的全谱：它要沿五条能力轴给模型画像。这五条轴值得你现在就记住，后面整本书都在为它们铺路：

  1. task execution——任务到底做没做成。
  2. world prediction（WAM / world model）——模型能不能预测世界接下来会怎样。
  3. safety reasoning——能不能预判危险、识别边界、拒绝危险动作。
  4. generalization——换物体、换场景、换后端、换渲染、换本体，还行不行。
  5. planning usefulness——它的世界模型真能帮上规划与安全决策吗。

从评测科学 看 为什么"五条轴"不是任性

测量理论里有个概念叫 construct validity（Jacobs & Wallach, FAccT 2021）：你的指标必须真的测到你声称在测的那个"构念"。把"具身智能"压成一个 success rate，就是典型的 operationalization gap——你声称在测"能力"，实测的只是"在某个固定分布上的成功率"。Raji 等人（NeurIPS 2021）干脆把这类号称通用的 benchmark 称作"Everything in the Whole Wide World Benchmark"，讽刺它们测不出自己宣称的普适能力。EOS 的五条轴，就是把这个"构念"显式拆开，让每条轴各自可问、可证。

和 MetaSim 划清的那条线

如果你听说过 MetaSim / RoboVerse（Abbeel、Malik 等人，arXiv:2504.18904），你可能会问：它不也是"统一很多仿真器"吗？EOS 用一句话把自己和它区分开，这句话值得抄在墙上：

招牌对照句

“MetaSim solves cross-simulator execution ergonomics; EOS solves evidence-backed embodied evaluation claims.”

MetaSim 解决的是跨仿真器的执行人机工程：一套配置、一个 Handler 接口，让你在 11 个仿真器上跑同一个任务（我们在 3.4 会细看它的 TensorState）。这非常有用，但它不替你回答"这个评测结论站不站得住"。EOS 把全部重量压在后一个问题上：它该被衡量的，不是支持了多少个仿真器、support matrix 有多宽，而是——它的 action / state / trace 证据，能不能支撑起关于任务成败、世界预测、安全推理、规划有用性、后端对比的结论。

本书会怎样区分"愿景"和"代码事实"

EOS 的文档里既有宏大的愿景语言（五条能力轴、五个 scenario pack、世界模型评测），也有此刻代码里真实跑得起来的地面真相（一个 SemanticProxyBackend 的 smoke、几个 live provider、一条视觉评测 lane）。这本书会把两者分开标注：讲愿景时说清"这是路线图"，讲机制时引真实的文件与类名。这本身就是 EOS 最核心的纪律——claim boundary：永远说清你这一步证明了什么、还不能证明什么。这个琥珀色的方框，全书都会用来标记这类"边界声明"。

这一节带走的

三件事就够进入下一节了：（1）EOS 不是又一个 benchmark，而是高一层的评测 OS——定义契约，让场景/后端/模型/度量都可替换，EBench 只是它的一个 adapter；（2）它沿五条能力轴给具身智能画像，把"能力"这个构念显式拆开；（3）它的立身之本是证据，不是仿真器覆盖面——这条线把它和 MetaSim 区分开。
