仓库星座：core / packs / adapters / backends

上一节给了你一句愿景："domain-agnostic, backend-composable evaluation OS"。但愿景不会自己变成纪律——纪律是被目录结构和依赖方向钉死的。这一节我们把整个仓库摊在桌面上，看清每一块负责什么、谁能 import 谁、以及那条"绝不反向"的依赖箭头。读完它，后面任何一节里出现的路径，你都能立刻知道它属于哪个"星系"。

先看一眼这棵树

EOS 是一个仓库，但内部被切成几个职责泾渭分明的区域。下面是顶层布局（省略了一些次要文件）：

embodied-eval-os/ (顶层布局)
src/embodied_eval_os/
  core/                      # 场景中立的契约层（domain-agnostic）—— 受 leakage checker 守护
    specs/                   #   TaskSpec / SceneSpec / BackendProfile / MetricSpec / ModelProfile ...
    state/                   #   EpisodeTrace / TraceStep / PhysicalStateProjection / TaskSemanticState
    primitives/              #   InteractionPrimitive / ProcessPrimitive / DevicePrimitive (三个 ABC)
    evaluators/              #   Evaluator(ABC) / MetricResult / EpisodeResult
    runtime/                 #   EpisodeRunner（Path A，in-process）/ EpisodeExecutionResult
    recorders/               #   TraceStore / Recorder
    reports/                 #   ReportGenerator / CapabilityProfile
scenario_packs/             # 场景语义（pipette、hazard taxonomy…）—— import core，绝不反向
  visual_manipulation_micro/ #   EVL-1 视觉 lane
  scientific_lab/            #   pipette/threaded-cap 语义 proxy 原语
adapters/                   # 被导入 benchmark 的概念（anti-corruption layer）
  ebench/                    #   EBench / GenManip 兼容靶子
  autobio/                   #   AutoBio readiness probe
  runtime_contract.py        #   adapter 产出 trace 的共享校验
backends/  renderers/  sensors/  control/   # 六大组件各自的实现侧
model_adapters/             # random_policy / scripted_policy / http_policy（真模型 sidecar）
runtime/                    # WorldSession、live model loop —— 注意：在顶层，不在 core
configs/backend_profiles/   # dummy_backend.yaml / mujoco_autobio.yaml / genesis_native.yaml ...
scripts/                    # check_core_leakage.py / check_architecture_debt.py ...
tests/                      # 守护上述边界的测试
examples/run_smoke.py       # 最小可跑路径
docs/  ( design/ operations/ records/ )

这棵树不是审美选择，而是三条铁律的物理外形。我们逐个区域过一遍它们各自"拥有"什么。

core 拥有契约，而不是语义

src/embodied_eval_os/core/ 是整座大厦的承重墙，它只放场景中立的契约（contracts），不放任何领域语义。它拥有的东西可以一口气数出来：specs/ 里的 TaskSpec / SceneSpec / BackendProfile / MetricSpec / ModelProfile；state/ 里的 EpisodeTrace / TraceStep / PhysicalStateProjection / TaskSemanticState；primitives/ 里的三个抽象基类；evaluators/ / recorders/ / reports/；以及 runtime/ 里那条简单的 in-process 评测路径 EpisodeRunner。

关键在于这里出现的名字都是抽象的：它知道"有一种东西叫 metric family"，但不知道 pipetting 或 contamination；它知道"有一种东西叫 process primitive"，但不知道 PipetteProxyPrimitive。任何一个具体场景的名字泄进 core，1.4 会告诉你 CI 会怎样让它红。

packs 拥有场景语义，adapters 拥有外来概念

scenario_packs/ 是场景语义的家。scientific_lab/ 把移液、拧盖、液量这些概念实现成 pack-local 的原语（subclass core 的三个 ABC），消费 core 给的 PhysicalStateProjection，把结果写进 TaskSemanticState 的 payload——core 永远不知道这些字段叫什么名字。visual_manipulation_micro/ 则是当前前沿 EVL-1 视觉 lane 的微场景。

adapters/ 是防腐层（anti-corruption layer）：所有被导入的外部 benchmark 概念都关在这里。adapters/ebench/ 装 EBench / GenManip 的兼容靶子，adapters/autobio/ 装 AutoBio 的 readiness probe。它们的活儿是把外部世界翻译成 core 的契约，而不允许反过来塑造 core 的 API。

从 EBench 看 从"一堆仓库"到"一个仓库 + 严格内部边界"

回忆一下 EBench 在你手里的样子：它其实是一个仓库星座——GenManip 仿真 server 一个仓、genmanip-client 一个仓、Assets 一个仓、Dataset 又一个仓，它们靠跨进程协议和约定松散地缝在一起。EOS 反过来：它把这一切收进一个仓库，再用严格的内部边界（目录划分 + 依赖方向 + leakage checker）取代"跨仓库的隐式约定"。换句话说，EBench 用"物理上的仓库分离"来隔离关注点，EOS 用"逻辑上的层分离"来隔离关注点——后者更难偷懒，因为所有代码都在同一个 import 路径下，唯一拦着你把 GenManip 写进 core 的，是纪律和脚本。

backends、model_adapters 与那个容易踩错的 runtime/

backends/、renderers/、sensors/、control/ 对应六大 backend 组件的实现侧（2.1 会细讲为什么后端必须被拆成六块）。model_adapters/ 装被评模型的接入：random_policy.py、scripted_policy.py，以及通往真模型 sidecar 的 http_policy.py。configs/backend_profiles/ 则是一堆 YAML，把六大组件的具体取值声明成可复用的 profile。

这里有一个最容易认错门牌的地方：顶层还有一个 runtime/ 目录（注意：不是 core/runtime/），它装的是 WorldSession 这个 live runtime 的 session 信封、以及 live model loop。它不在 core 里，因为它要触碰具体后端的生命周期与原生 artifact，是脏活；而 core/runtime/ 里的 EpisodeRunner 是干净的、in-process 的、不绑任何引擎的那条简单路径。两个 runtime，一个在核心一个在顶层，差别正是"契约 vs 实现"。

两个 runtime，别认错

core/runtime/episode_runner.py（干净、in-process、Path A）vs 顶层 runtime/live_model_loop.py（脏、绑后端、Path B）。我们在 6.1 会把两条路径并排剖开。

那条绝不反向的箭头

现在说这一节真正的"核心思想"——它比目录布局重要得多。所有这些区域之间的依赖，只能朝一个方向流：

依赖方向（绝不反向）
core  ←  scenario_packs
core  ←  adapters
core  ←  backends / renderers / sensors / control
core  ←  model_adapters

读法是：scenario_packs、adapters、backends、model_adapters 都可以 import core（它们要用 core 的契约），但 core 永远不许 import 它们。core 不知道 EBench 存在、不知道 scientific_lab 存在、不知道 MuJoCo 存在。这正是"domain-agnostic"在代码层面的精确含义：核心对所有具体场景与后端一无所知，所以才能服务于任意场景与后端。

这条箭头不是靠 code review 的善意维持的，而是靠 scripts/check_core_leakage.py 强制的：它扫描 core/**/*.py，一旦发现 ebench / genmanip / pipette / mujoco 这类禁词（大小写不敏感、按子串或词边界匹配），就让检查失败、CI 变红。也就是说——"反向依赖"在物理上还没发生，名字泄漏就先被拦下了。

这张目录树证明了什么、还不能证明什么

目录结构 + 依赖方向 + leakage checker，能证明的是"核心在静态层面保持了 domain-agnostic、没有被某个场景或某个仿真器反向塑造"。它不能证明的是"任何一个场景包真的跑通了""任何一个后端真的产出了可比证据"。一个干净的依赖图是必要条件，不是评测结论本身——结论永远要回到 trace 证据（1.1）。架构整洁是地基，不是楼。

这一节带走的

把这张地图记进肌肉记忆：core 拥有契约（specs/state/primitives/evaluators/runtime/recorders/reports），scenario_packs 拥有场景语义，adapters 拥有外来 benchmark 概念，backends/renderers/sensors/control 拥有六大组件实现，model_adapters 拥有被评模型接入，顶层 runtime/ 拥有 WorldSession 与 live loop（不在 core）。而把它们粘在一起的不是耦合，是一条绝不反向的依赖箭头：core ← 其它一切，由 leakage checker 站岗。
