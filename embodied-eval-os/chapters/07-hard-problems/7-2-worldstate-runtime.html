WorldState Runtime：从同起点到首次分叉

上一节修好了"从同一个起点出发"。但有人盯着两段 pickup 视频反复看：MuJoCo 里试管被稳稳拎起，Genesis 里它滑脱了。一开始大家以为这是个 bug。后来才意识到——这不是 bug，是地基没打的症状。WorldState Runtime（WR）这场长达八个里程碑的战役，就是去打那块地基。

视频不一致只是症状

WR 的开端是一个诱人的陷阱：既然 AutoBio 的 pickup 任务在两个引擎里表现不同，那就去"修好"它，让 Genesis 也能拎起试管。但项目做了一个反直觉、却决定全局走向的判断——pickup 视频不一致，是一个"缺地基"的症状，而不是一个待修的任务 bug。真正缺的，是一套能让任意两个后端"被测量、被投影、被比较、被审计"的运行时底座。

于是发生了这场战役里最重要的一次身份调整：AutoBio 任务从"架构拥有者"被降级为"regression scenario"。它不再是组织架构的那根主轴；架构的主轴换成了通用的 WorldState Runtime Foundation（WR-0…WR-6），AutoBio pickup 只在最后作为一条回归场景挂上去。"别让一个 benchmark 反过来定义你的 OS"这条铁律，在这里第一次以血的代价被执行。

L2/L3 清算：三轴解耦

地基要打好，先得把混在一起的概念拆开。2026-06-05 的 l2-l3-layering-clarification 记录直指当时反复纠缠的三个问题：L2 要不要用 live USD stage 当世界的主表示？Genesis 要不要每一步把内部状态镜像进 USD？要不要推倒重做 L2？记录的回答是：这些混乱，都来自把三件正交的事搅在了一起。

docs/records/2026-06-05-l2-l3-layering-clarification.md
layer ownership      (L0-L6)
interchange format   (USD / MJCF / solver decks)
runtime truth        (MuJoCo / Genesis / PhysX / real robot / CAE internals)

把它们分开后，规则就清晰了：L2 WorldSession 是 session envelope（信封），不是世界存储——它记录哪个 backend profile 在跑、生命周期、时钟、端口、topology 的引用，但不拥有 per-step 物理真相。per-step 的 pose、qpos、contacts、solver coverage，属于 L3 RuntimeMeasurementSnapshot，由 measure() 在 reset / event 边界产出。跨后端比较用 L3（或 L3→L4 投影），而不是看磁盘上某个 .usda 文件有没有变。这条记录里那句北极星，值得抄下来：

北极星

"Under the same task and evidence rules, different physics backends produce results that can be measured, projected, compared, and audited without overclaiming."

WR-7 转折：从"同起点"到"首次分叉"

地基铺好后，WR-7 带来了整场战役的认知转折。在此之前，问题被框成"两个引擎能不能从同一个起始状态出发"——这是一个关于 reset 的静态问题。WR-7 把它重新提问了：与其纠结"起点能不能对齐"，不如问——两个引擎沿时间推进，在哪一步第一次分叉？

这个提问的转变，把评测对象从"一张快照"换成了一条 paired dynamic trace：让两个引擎重放同一条动作序列，沿若干条轴同步采样，找出每条轴的 first-divergence step。这些轴不是随便选的，而是覆盖了从控制输入到任务语义的整条因果链：

paired dynamic trace · 分叉轴
robot_action_replay        重放的动作是否对齐
tube_lift                  试管是否被抬起
finger_cap_contact         手指与试管帽是否接触
tube_cap_body_retention    帽/管是否保持在一起
contact_force              接触力
task_phase_semantics       任务阶段语义

把这些轴对齐到同一时间轴上，"哪个引擎更对"这种含糊问题，就被替换成可记账的"在第几步、哪条轴上，两者第一次不一致"。WR-7D 那个里程碑的 gate_status=failed，恰恰是这套方法有用的证据——它是一次成功的诊断，而不是一次 parity 声称。下面这个部件，让你拖动时间轴亲眼看分叉点逐条轴亮起。

从物理后端 看 分叉不是 bug，是引擎的本性

两个引擎从同一起点喂同一条动作，为什么必然会分叉？因为接触动力学本质是一个非线性互补问题（NCP），而每个引擎为了速度和稳定，各自做了不同的松弛：把摩擦锥线性化（→ LCP，摩擦力方向与真实速度错开）、或软化互补条件（→ 引入非物理穿透）。SimBenchmark（RaiSim/Bullet/ODE/MuJoCo/DART）实测到各引擎的位置漂移表现是任务相关的；布料 sim-to-real 基准里，准静态任务大家都低误差，动态任务却没有任何引擎精确匹配。所以 WR-7 测到的"首次分叉"不是哪个引擎写错了——它在测量两套求解器近似之间真实存在的鸿沟。EOS 能做的，只是把这条鸿沟测准、记清，而不是假装它不存在。

interactivepaired dynamic trace：拖时间轴找 first divergence
拖动时间轴。每条轴在它的 first-divergence step 之前是 matched，之后翻成 mismatched——比较的产物是"何处分叉"，不是一个总分。

两条 Genesis 车道：raw vs primitive-assisted

WR 还逼出一个诚实的细分。Genesis 在"裸物理"下（raw lane）拎不起试管；但如果允许 pack 用一个 ProcessPrimitive 去辅助保持（primitive-assisted lane），上层任务语义就能成立。于是 Genesis 被拆成两条车道，分别记账——绝不把"辅助车道成立"偷换成"裸物理成立"。

WR-8H 关闭的，正是一个车道范围（lane-scoped）的 L3 任务语义 outcome：

WR-8H · lane-scoped outcome
primitive_assisted_genesis_l3_task_semantic_outcome = true
raw_genesis_lane_task_success                       = false

注意视频在这里的地位：它只作为 visual support，是辅助性的视觉佐证，而不是判定 outcome 的证据本身。判定靠的是 L3 测量与逐轴账本，视频只是让人类看得见。

WR 阶段诚实收尾：能说什么、不能说什么

能说：在同一任务与同一证据规则下，两个引擎在哪些轴一致、在哪一步分叉；primitive-assisted 车道支撑了某个上层任务语义 outcome。不能说：Genesis 的 native physics 复现了 MuJoCo 的 pickup physics。一个 assisted-lane 的 L3 outcome 成立，不等于裸引擎物理等价；视频好看，不等于 trajectory parity 或 contact-force parity。这正是 0.1 立下的 claim boundary 纪律，在一场真实战役里被一字一句地守住。

这一节带走的

三点：（1）pickup 视频不一致是缺地基的症状，导致 AutoBio 任务从架构拥有者降级为 regression scenario；（2）L2/L3 清算用三轴解耦（layer ownership / interchange format / runtime truth）把混乱拆开，L2 是 session envelope、L3 才是跨后端证据；（3）WR-7 把问题从"同起点"转向"首次分叉"，用 paired dynamic trace 逐轴记账，并以 raw / primitive-assisted 两条车道诚实区分——assisted lane 成立不等于 Genesis native physics 复现了 MuJoCo pickup。
