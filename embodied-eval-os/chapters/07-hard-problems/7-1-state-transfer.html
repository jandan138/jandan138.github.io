跨引擎状态迁移：qpos 拷贝的坑

这一 Part 不再讲架构应该长成什么样，而讲它怎么被打疼的。每一节背后都有一场真实的工程战役，记录在 docs/records/ 里。第一仗，是一个安静到几乎没人察觉的 bug：一段 qpos 向量，被按数值下标从一个引擎拷到另一个引擎——两边的关节排布根本不一样。机器人没报错，只是手指穿进了试管壁里。

stage50：一段向量，两套关节

故事发生在 Genesis-owned 执行那条线上（records 2026-06-01~03）。当时的目标朴素得很：拿一个在 MuJoCo 里已经摆好的初始状态——机器人手臂的关节角、试管在 rack 里的位姿——原样搬到 Genesis 里去，让两个引擎从同一个起点出发。最直接的写法，就是把 MuJoCo 的 qpos 数组整段读出来，再整段写进 Genesis。一行 numpy 切片的事。

它跑通了。没有异常，没有断言失败，trace 也照样产出。直到有人去看渲染：Genesis 里的夹爪手指穿过了试管帽，试管整个嵌进了 rack 槽位的几何体里——interpenetration 与 clipping，肉眼可见的物理崩坏，却没有任何一行日志提到它。这就是 stage50 bug：一个 silent 的错误。

原因一旦说破就很蠢，但正因为蠢才危险：MuJoCo 的 qpos 第 7 个分量，可能是某个手腕关节；Genesis 的 qpos 第 7 个分量，可能是夹爪开合。两个引擎在内部按各自的顺序排列自由度——关节、body、contact 的排序从来没有被约定要一致。按下标对齐，等于把"手腕角度"写进了"夹爪开合"。数字全都"成功"地落了位，语义却全错了。

从物理后端 看 同下标 ≠ 同自由度

不同引擎对 DoF / body / contact 的排序，是各自的实现细节，没有跨引擎契约。MetaSim 的 TensorState 之所以要把 DoF 按 lexicographical order 重排，正是因为"裸下标"不可携带（我们在 3.4 拆过这个陷阱）。更深的层面：跨引擎本来就难对齐——接触是一个 non-smooth complementarity problem，各引擎为了速度与稳定各自松弛（线性化摩擦锥、软化互补、允许穿透）。SimBenchmark 测 RaiSim / Bullet / ODE / MuJoCo / DART，发现引擎表现高度 task-dependent；cloth manipulation benchmark 里，dynamic 工况下没有任何一对引擎精确匹配。在这种现实下，"把一段向量按位置拷过去就当作同一个状态"，是一个范畴错误（category error），不是一个数值精度问题。

修法：按名字重映射，缺了就 hard-fail

修复的思路很直接：不按下标，按关节名字（joint name）重映射。源引擎里的 wrist_2_joint 必须落到目标引擎里那个同样叫 wrist_2_joint 的自由度上，而不是落到"恰好排第几位"的那个。更关键的是第二条：如果目标引擎里找不到某个关节，或者两边的向量宽度对不上，立即 hard-fail，而不是悄悄截断、补零、或跳过。

这条"宁可炸、不要静默"的纪律，正是 1.3 讲的 No Silent Fallback Policy 在状态迁移上的具体化身：缺了关节，是一个显式的 blocked_missing_state，不是一次"看起来成功"的迁移。下面这个部件，让你亲手对比这两种拷贝。

interactivestage50：按 index 拷贝 vs 按 joint name 重映射
切换两种迁移方式。按 index 拷贝时数字"全部就位"却物理崩坏；按 joint name 重映射时，对不上的关节会被标成 blocker 而不是被悄悄吞掉。

升华进 core：generic-state-transfer-contract

一个 bug 被修好还不算完。EOS 的习惯是问：这个教训能不能变成一条谁都绕不过去的契约？于是它被升华进了 core 的 generic-state-transfer-contract。注意这里的纪律——契约必须是 domain-agnostic 的：core 不知道"试管""rack"，它只知道抽象的状态分量与映射条目。

契约引入了两个结构：StateComponentSpec 描述"一个状态分量是什么"（它的语义身份、它在某个后端里的布局），StateTransferMapEntry 描述"源的哪个分量映射到目标的哪个分量"。有了它们，状态迁移就从"拷一段数字"变成"按显式映射搬运被命名的分量"。而最重要的一条判决写进了规则里：

这条契约证明了什么、拒绝了什么

generic-state-transfer-contract 让一次跨引擎迁移可审计：每个被搬运的分量都有语义身份与映射来源，缺失与宽度不符都是显式 blocker。它不证明两个引擎物理等价，也不证明迁移后轨迹会重合——它只保证"我们搬的是同一个被命名的东西"。它最强硬的一条是：一段没有布局身份（layout identity）的裸向量，本身就是一个 structured blocker。换句话说，光给一段 qpos 数字、不给"每个分量是哪个关节"的布局，在 EOS 里不构成可迁移的状态——它会被当作缺证据，而不是当作成功。

这条"裸向量即 blocker"的规则，和 3.4 里"为什么不用裸 TensorState"是同一种世界观的两面：同一个 shape、同一段数字，并不能证明两边有相同的 component inventory、相同的 joint-body-actuator-contact 排序、可比的 frame / unit / sign / force family。stage50 不是个例，它是这个世界观被一次惨痛的渲染画面验证了。

这一节带走的

三点：（1）stage50 bug 的本质是按数值位置跨引擎拷贝 qpos，在关节排布不同的两个后端间制造了静默的 interpenetration——这是范畴错误，不是精度问题；（2）修法是按 joint name 重映射 + 缺关节/宽度不符就 hard-fail，让迁移失败变成显式 blocker；（3）教训被升华进 core 的 generic-state-transfer-contract（StateComponentSpec / StateTransferMapEntry），并立下"裸向量无布局身份 = structured blocker"的硬规则。

但"从同一个起点出发"只是序章。下一节我们走进 WorldState Runtime 那场大战役——当两个引擎确实从同一状态启动后，真正的问题变成了：它们会在何时何处第一次分叉？
