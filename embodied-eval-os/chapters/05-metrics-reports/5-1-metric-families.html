Metric family（core）vs metric instance（pack）

在 EBench 里，一个 metric 就是一个写死的函数：算 success rate、算 path length、算 collision count。但在一台要评测任意场景的 OS 里，core 不可能知道"liquid volume error"或"part alignment"长什么样——它只能预先约定一组抽象的度量家族，再把"具体测什么、单位是什么"留给 scenario pack 去实例化。这一节，我们就把 metric 这件事拆成 family（核拥有）和 instance（包拥有）两层。

为什么 metric 也要分两层

回忆铁律一：core/ 必须 domain-agnostic。一旦你在 core 里写下一个叫 liquid_volume_error_ul 的度量，core 就被"科学实验室"这个场景污染了——下一个想接入 EOS 的工厂装配场景根本不关心微升。所以 core 在度量层面只允许存在一种东西：family（家族），一个关于"这一类度量在评测什么维度"的抽象坐标，而不是任何一个具体度量。

具体的度量——它的名字、单位、取值范围、方向、需要 trace 里哪些字段——则是 实例，由 scenario pack 在自己的 metrics/metric_spec.yaml 里声明，并标注它属于哪个 family。一句话：

Core defines the abstract metric families; scenario packs instantiate the concrete metric instances.

家族清单（以及一处诚实的文档不一致）

core 认可的 metric family 是一张短而稳定的清单。主清单是这八个：

  • task_outcome——任务到底做没做成。
  • procedure——流程/步骤序是否合法。
  • state_transition——状态转移本身（预测 vs 真值）的误差。
  • precision——量化的精度类误差（位置、体积、对位…）。
  • hazard——危险检测、误报漏报、安全边界。
  • prediction——世界模型对未来的预测质量。
  • planning——预测/世界模型对规划与决策是否有用。
  • resource——时间、步数、算力等代价。

现在到了本书的纪律时刻——我得诚实地告诉你文档里有不一致，而不是替它打圆场：

两个"幽灵家族"

restoration（复原/归位类度量）只出现在 docs/design/metric-system.md 里；而 generalization（泛化）只出现在 README、scenario-pack 文档和 reporting 文档里，没出现在 metric-system 的家族枚举中。换句话说，今天没有一处单一文件能给出"权威全集"。我把它们照实列出来，但请把它们当作正在收敛中的设计，而不是已冻结的 API。把 generalization 当成一条报告轴（见 5.2）通常比当成一个 metric family 更稳妥。

注意：family 永远是抽象的。你不会在 family 清单里看到 pipetting、contamination、conveyor 这种场景词——那些是 instance 的事。family 决定的是"这条度量挂在能力画像的哪根轴上"。

代码里的真实类型

愿景说完，落到地面。打开 core/evaluators/base.py，你会发现 core 在度量这件事上其实只定义了三个朴素的数据结构和一个抽象基类——刻意地小：

src/embodied_eval_os/core/evaluators/base.py
@dataclass
class MetricResult:
    name: str
    value: float | int | bool | str
    family: str
    unit: str | None = None
    details: dict[str, Any] = field(default_factory=dict)

@dataclass
class EpisodeResult:
    episode_id: str
    task_id: str
    metrics: list[MetricResult] = field(default_factory=list)
    summary: dict[str, Any] = field(default_factory=dict)

class Evaluator(ABC):
    evaluator_id: str
    def evaluate_step(self, state, **kwargs) -> list[MetricResult]:
        return []
    @abstractmethod
    def evaluate_episode(self, trace) -> EpisodeResult:
        ...

请注意 MetricResult 上那个 family: str 字段——这就是 family/instance 两层结构在代码里的缝合点。一个 instance（比如名为 liquid_volume_error_ul 的结果）在运行时携带它属于哪个 family（"precision"），于是报告生成器（第 6 章会再见到它）能把成百上千条 instance 自动归并到那八根抽象轴上，而 core 始终不必认识任何一个具体度量的名字。

Evaluator 是 ABC：evaluate_step() 默认返回空列表（不是每个评测器都逐步打分），evaluate_episode(trace) 是必须实现的——它吃一整条 EpisodeTrace，吐一个 EpisodeResult。core 里有三个具体子类作为通用评测器（注意它们的名字也全是 domain-agnostic 的）：

  • TaskOutcomeEvaluator——把 trace 收束成任务成败（examples/run_smoke.py 用的就是它）。
  • HazardEvaluator——聚合 trace 里的 hazard_events，算出诸如 max_hazard_severity 之类的安全量。
  • PredictionEvaluator——比对世界模型的 PredictedFuture 与实际发生的状态。

这三个评测器恰好覆盖了 outcome / hazard / prediction 三个最通用的 family——它们之所以能进 core，是因为它们对每个 scenario pack 都有用，通过了 Core Entry Test。而 liquid_volume_error_ul 这种东西永远进不来。

MetricSpec：实例的声明书

那 pack 怎么声明一个 instance？靠 MetricSpec（一个进了 core 的契约类型——它本身是 domain-agnostic 的"度量声明的形状"，而被填进去的内容才是场景特定的）。它的字段是：

scenario_packs/scientific_lab/metrics/metric_spec.yaml（示意）
metric_id: liquid_volume_error_ul
name: "Liquid volume error"
family: precision              # 挂到哪根抽象轴
scenario_pack: scientific_lab
description: "Aspirated/dispensed volume error vs target"
unit: microliter
range: [0, 1000]
target_direction: lower_is_better   # higher_is_better | lower_is_better | target_value
uses_privileged_state: true          # 这是 evaluator_only 的真值
supported_model_families: [actor_policy, vla, world_model]
required_trace_fields: [task_semantic_state.process_state.dispensed_volume_ul]
failure_modes: [missing_volume_projection, no_target_set]

三个字段在这里特别要紧。family 决定归并轴；uses_privileged_state 诚实地标出这条度量依赖 model 看不到的真值（见 5.3 的可见性模式）；required_trace_fields 把度量和 trace 绑定——如果某条 trace 缺了这些字段，对应度量不能偷偷填 0，而要进入 blocked_missing_measurement 状态（铁律三，No Silent Fallback）。

几个真实 instance，挂回各自的 family

把抽象家族落到一组真实实例上，你立刻能看清这套两层结构的好处——不同场景、不同度量，却共享同一组报告轴：

instance → family 映射（跨四个 pack）
scientific_lab  liquid_volume_error_ul        → precision   (microliter, privileged)
scientific_lab  sample_transfer_success       → task_outcome
scientific_lab  protocol_step_validity        → procedure
wetlab_safety   dangerous_action_detection_rate (DDR) → hazard
wetlab_safety   state_transition_error  (STE)  → prediction
factory_assembly part_alignment_error_mm       → precision   (mm)
field_robotics  rollover_risk_detection_rate   → hazard

看 liquid_volume_error_ul（微升）和 part_alignment_error_mm（毫米）：两个毫不相干场景里的度量，单位、范围、含义全不同，却都属于 precision 家族——于是它们在 capability profile 上落到同一根精度轴，让"科学实验室里的策略 vs 工厂装配里的策略"在精度维度上变得可对照，而 core 一行场景代码都没写。这正是 family/instance 分层换来的东西。

从 EBench 看 从"一堆指标函数"到"一张归并表"

EBench 的诊断报告里，每条指标基本是手写的、和 home-manipulation 任务焊死的。EOS 没有抛弃这些指标——它把每条指标重新表述成一个携带 family 的 MetricResult，于是"EBench 的 success rate"变成一个 task_outcome family 的 instance，"路径长度"变成 resource family 的 instance。换句话说，你在 EBench 学到的所有度量都还在，只是被贴上了一张能跨场景归并的标签。

这一层证明了什么 / 没证明什么

family/instance 分层证明的是：EOS 能在不污染 core 的前提下，把异构场景的度量归并到一组稳定的能力轴上。它没有证明任何一条 instance 在该场景里"测得准"——liquid_volume_error_ul 用的是 semantic liquid proxy，不是真流体动力学；它落在 precision family 这件事，只说明它声称测精度，不等于它测到了真实的物理精度。"度量挂对了轴"和"度量本身有效"是两回事——后者的 claim boundary，留到 5.4 专门清算。

这一节带走的

三点：（1）core 只拥有抽象 family（task_outcome / procedure / state_transition / precision / hazard / prediction / planning / resource，外加文档仍在收敛的 restoration 与 generalization），pack 通过 MetricSpec 实例化具体 instance；（2）代码里这套结构缝合在 MetricResult.family 字段上，加三个通用评测器 TaskOutcomeEvaluator / HazardEvaluator / PredictionEvaluator；（3）family 让异构度量可跨场景归并，但归对轴 ≠ 测得准。
