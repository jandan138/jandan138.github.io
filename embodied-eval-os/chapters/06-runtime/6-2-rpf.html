Runtime Provider Facade：八个动词

路径 B 的心脏，是一个叫 Runtime Provider Facade（RPF）的东西。它的工程外形——一个暴露若干动词、按需懒加载某个后端的 facade——是从 MetaSim 借来的。但 EOS 借的只是形状，它明确拒绝了 MetaSim 那套外形所隐含的两条假设。这一节我们就来拆这八个动词，看它们如何既像一个仿真器接口、又坚决不把"调通一个 SDK"当成"评测结论"。

借外形，拒含义

MetaSim / RoboVerse 的工程做法很优雅：用一套统一配置，配上每个仿真器一个 Handler（MujocoHandler、IsaacLabHandler、PybulletHandler…），对外暴露一组生命周期方法。EOS 看中的是这个"暴露动词的 facade + 懒分派"的工程形状——它干净、可测、好扩展。但 EOS 在 metasim-runtime-boundary-review 里明确写下：不依赖 MetaSim、不抄它的 API，只借外形。

因为那个外形悄悄夹带了两条 EOS 不能接受的含义：

  • "一个 handler = 一个 backend"。EOS 的铁律三说后端必须拆成 platform / physics / renderer / sensors / control / process runtime 六个组件。一个 MujocoHandler 把这六件事打包成"MuJoCo"——这正是 EOS 要避免的单字符串身份。
  • "handler state 物理可比"。从两个 handler 各自 get_state() 拿到同形状的 tensor，不等于它们的 joint/body/contact ordering、单位、符号、力家族可比（这是 3.4 的全部主题）。
从物理后端 看 MetaSim 的生命周期没有"恰好八个动词"

说清楚一件事，免得你读了 MetaSim 论文回来对不上号：MetaSim 的 BaseSimHandler 暴露的是 launch / get_state / set_state / simulate / close 这一组生命周期方法（外加 get_joint_names / get_body_names 之类），论文里并没有"恰好八个动词"的清单。EOS 的八个动词是 EOS 自己的设计，是把"懒分派 facade"这个外形重新切分、再补上 EOS 特有的证据语义（measure 与 query 的分离、apply_control 要回 ack）后的产物。不要把 EOS 的八动词说成 MetaSim 的接口。

八个动词

facade 的契约就摆在 runtime/provider_facade.py 里，八个方法签名清清楚楚：

src/embodied_eval_os/runtime/provider_facade.py
class RuntimeProvider(Protocol):
    def materialize(self, ...): ...     # 把 scenario 声明的世界拉成一个 WorldSession
    def reset(self, ...): ...           # 回到初始 episode 状态
    def apply_state(self, ...): ...     # 写入一个外部状态（受 capability 限制）
    def apply_control(self, ...): ...   # 把控制请求交给后端，回一个 ack
    def step(self, ...): ...            # 推进一拍物理
    def measure(self, ...): ...         # 抓一张 artifact-backed L3 测量快照
    def query(self, ...): ...           # 取诊断/telemetry/native dump 等旁路证据
    def close(self, ...): ...           # 收尾，释放 session

前七个动词驱动一次 run 的主干，query 与 close 是辅助。它们各自的职责边界很重要：measure 产出的是证据边界——一张 artifact-backed 的 L3 RuntimeMeasurementSnapshot（不可变、hash 寻址、capability-scoped）；而 query 取的是旁路诊断（process-runtime telemetry、solver diagnostics、native state dump），它们可能有用但不构成主证据线。把"测量"和"查询诊断"分成两个动词，本身就是在防止"拿后端的 native dump 当跨后端证据"这种偷换。

facade 还在类型层面守纪律：每个动词返回一个 RuntimeProviderOperationResult，当 status 落在 {blocked, failed, unsupported} 时，blocking_reasons 必须非空——代码里直接断言"不许有沉默的 blocked"。这就是 no-silent-fallback 政策在 facade 这一层的兑现：一个动词失败了，你拿到的不是 0，是一条写明缘由的 blocking reason。

interactive八动词 facade：驱动一个 episode，看模型被脱敏的那一刻
按时序点过八个动词，看一次 run 怎样被驱动；特别留意 measure 之后、动作进模型之前，privileged / native-dump / solver-diagnostics 是怎样被挡在 model-visible observation 之外的。

单个 simulator 字符串不是 backend identity

这是 RPF 最该刻进脑子的一条：在 EOS 里，"simulator: mujoco"这样一个字符串，不是一个 backend 身份。一个 provider 即便底层确实是 MuJoCo，它的身份也必须由六组件 + capability 声明来描述——physics 是 MuJoCo 不代表 renderer 也是它，更不代表它在某条轴上就是 exact。facade 的证据边界是 provider 产出的 artifact-backed L3 结果，不是它喊自己叫什么。这也是为什么 RPF 从不以"支持了几个 handler"来自我衡量——support-matrix 的宽度不是 EOS 的产品边界。

RPF 是怎样一关一关打下来的

RPF 不是一次写成的，它的闭环史（记在 docs/records/ 与 index.md 里）本身就是一段"先立边界、再上真后端"的纪律示范，从 RPF-1 一路到 RPF-10：

  • RPF-1→6：纯架构地基——boundary & claim freeze、provider facade 契约规格、runtime protocol 骨架、query-evidence 集成、external-solver adapter pilot、pickup-bridge。这六关里没有一个真仿真器，全在把契约钉死。
  • RPF-7A：第一个 fresh 的 MuJoCo 3.3.0 live provider，状态 executed_pass，跑出了真实的 motion_delta。这是 facade 第一次真的拉起一个物理后端。
  • RPF-7B：fixture-driven 的通用 provider conformance kit——用固定 fixture 判一个 provider 合不合契约，而不按它支持多少 handler 来打分（这条 6.4 会细讲）。
  • RPF-8：scenario / materialization 驱动——让 scenario 声明世界长什么样，而不是 provider 自己手写 MJCF。世界的所有权回到了 scenario pack。
  • RPF-9：第二、第三个 live provider 上线——PyBullet 与 Genesis 0.4.4，证明 facade "不止 MuJoCo"。
  • RPF-10：PyBullet 上挂一个 scripted_demonstrator 的 live model loop（privileged_state_visible_to_model: false、standard_model_score: null）——也就是 6.3 要拆的那条链。

注意这条曲线的形状：先关六关纯契约，第七关才碰真后端。这正是 EOS 与"先接十个仿真器再说"的工程文化的分野——它要先确定"什么算证据"，再去产证据。RPF-11（parallel / hybrid 执行）是可选项，不是默认的下一步。

一个 live SDK lane 证明了什么 / 还不能证明什么

RPF-7A 把 MuJoCo 真的拉起来并跑出 motion_delta，这证明的是：EOS 的 facade 能在一个真实物理 SDK 上执行一条 live lane，并把产物做成 artifact-backed 的 L3 证据。它不证明三件互不相同的事——a live SDK lane ≠ a benchmark score ≠ backend parity。"我成功调用了 MuJoCo 的 step"不等于"模型在这个任务上的得分成立"，更不等于"MuJoCo 与 PyBullet 在这条轨迹上物理等价"。RPF 的全部纪律，就是把这三件事在报告里分开声明，永远不让"调通 SDK"悄悄升级成"评测结论"或"后端等价"。

这一节带走的

RPF 借了 MetaSim 的工程外形（暴露动词的懒分派 facade），但拒绝了它的两条含义——"一个 handler = 一个 backend"和"handler state 物理可比"。它的八个动词是 materialize / reset / apply_state / apply_control / step / measure / query / close（这八个是 EOS 自己的，不是 MetaSim 的）；measure 产出 artifact-backed 的 L3 证据边界，单个 simulator 字符串不构成 backend 身份。它的闭环史 RPF-1→10 先关六关纯契约、第七关才上真 MuJoCo，再到 PyBullet/Genesis 多后端与 RPF-10 的 live model loop。
