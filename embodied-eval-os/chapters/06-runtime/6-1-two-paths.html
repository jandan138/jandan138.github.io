两条评测路径：EpisodeRunner vs provider loop

到现在为止，你已经知道一条 EpisodeTrace 长什么样、它为什么是证据、状态怎样分三层归一化。但 trace 不会凭空出现——总得有什么东西真的把后端拉起来、把动作喂进去、把测量抓出来，最后把这一切缝成一条 trace。这一节就来看 EOS 用来"产出 trace"的两条路径：一条朴素得几乎像玩具，一条是当前前沿的 live 证据链。理解它们为什么共用同一套状态契约、却走两条代码路，是读懂整个 runtime 层的钥匙。

为什么会有两条路

一个评测 OS 面对两类截然不同的需求。第一类：我只想快速把"后端 + 模型 + 任务"拼起来跑一遍，证明这条管线在 Python 进程内能闭合、能吐出一条结构正确的 trace。它不碰真实仿真器的 SDK，不要求毫秒级保真，只要求结构与证据契约是对的。第二类：我要把一个真实的物理后端（MuJoCo、PyBullet、Genesis）当作 provider 拉起来，让模型在脱敏后的观测上做决策，把每一步的产物都做成 hash 寻址的证据，最后判定"这一步证明了什么"。

这两类需求若塞进同一段代码，必然互相拖累——前者会被后者的 artifact 机制压垮，后者会被前者的简化假设污染。EOS 的选择是两条路径、一套契约：无论走哪条，最终都落到 EpisodeTrace / PhysicalStateProjection / TaskSemanticState 这三个 core 概念上。路径可以换，证据的形状不能换。

从 EBench 看 一个 client–server loop 裂成了两条

在 EBench 里你只见过一种评测循环：client 连上 GenManip server，reset → step → close，仿真器是个黑盒，模型隔着进程边界喂动作。那套循环非常具体——焊死在 Isaac 4.1、Lift2 本体、固定的 camera 名上。EOS 把这条 loop 的意图抽出来，一分为二：一条退化成进程内的 EpisodeRunner（连黑盒都省了），一条升格成通用的 provider 证据链（黑盒变成可换的物理后端）。EBench 那条 loop，现在只是后者的一个特例。

路径 A：进程内的 EpisodeRunner

路径 A 的全部实现就在 core/runtime/episode_runner.py 里，短到可以一口气读完。它是一个 @dataclass，把四样东西拼在一起，再加一个步数上限：

src/embodied_eval_os/core/runtime/episode_runner.py
@dataclass
class EpisodeRunner:
    backend: EpisodeBackend
    model: EpisodeModel
    task_spec: TaskSpec
    scene_spec: SceneSpec
    max_steps: int = 100

    def run(self, seed: int | None = None) -> EpisodeTrace:
        ...

关键在于 backend 和 model 都不是具体类，而是 Protocol——结构化的鸭子类型契约。EpisodeBackend 只要求实现 load_scene / reset / step / measure / project_physical_state；EpisodeModel 只要求 reset / act。任何满足这两个协议形状的对象，都能插进 runner。这就是"后端可换、模型可换"在最朴素层面的兑现：runner 自己对 MuJoCo、对随机策略、对任何东西一无所知。

run(seed) 的流程是教科书式的：load_scene → reset → 循环里 model.act(obs) → backend.step(action) → measure() → project_physical_state()，每步组一个 TraceStep 追加进 trace，直到 terminated/truncated 或步数耗尽。注意它没有填充 TaskSemanticState 的语义字段（路径 A 留空一个空壳），因为场景语义是 pack 的事，不是这个通用 runner 的事。

被强制写进每条 trace 的东西

路径 A 虽然朴素，却已经在执行 EOS 的两条铁律。第一，它把后端拆成六个组件强制记进 trace——这个常量就摆在文件顶部：

src/embodied_eval_os/core/runtime/episode_runner.py
STANDARD_BACKEND_COMPONENTS = (
    "platform", "physics", "renderer", "sensors", "control", "process_runtime",
)

哪怕你只给了一个 backend id，_backend_components() 也会先把这六个键铺成 None，再用后端显式声明的部分覆盖。换句话说，runner 在结构上拒绝"这个后端就是 MuJoCo"这种单字符串身份——六个槽位永远在那里提醒你：platform、physics、renderer 是三件不同的事。

第二，它记录 provenance。_current_repo_commit() 用 git -C <repo_root> 取所属仓库的 HEAD，而且刻意忽略当前工作目录——有一条测试专门守着这一点。为什么这么较真？因为 trace 的 versions 里那个 repo_commit 必须指向"产出这条 trace 的那份代码"，而不是"恰好运行命令时所在的目录"。没有可信的 commit，trace 就不是有效证据。同样默认写入的还有那句 claim_boundary="Trace evidence only; no simulator fidelity or real-world safety claim."——朴素归朴素，边界声明一个字都不能少。

这条路谁在走？examples/run_smoke.py 就是它的标准用法：用一个 SemanticProxyBackend 配 RandomPolicyAdapter(delta=0.4)，max_steps=10，run(seed=42)，再交给 TaskOutcomeEvaluator().evaluate_episode(trace)，需要时用 TraceStore 落盘成 JSON。这就是每次 PR 前必跑的那个 smoke——它证明的不是"评测对了"，而是"管线契约没断"。

路径 B：provider / evidence-chain live loop

路径 B 是另一个世界。它住在 runtime/live_model_loop.py（注意是 runtime/ 而非 core/——live session 的东西不进 core），入口是 run_rpf10_live_model_loop。它不再把后端当 Protocol 的薄壳，而是把它当成一个 provider：通过一个暴露八个动词的 facade（materialize / reset / apply_state / apply_control / step / measure / query / close）驱动一次真实 run。每一步的产物——观测帧、控制 ack、测量快照、求解器诊断——都做成 hash 寻址的 ArtifactRef，最后缝成 trace，并生成一份 report.json，里头一排 claim_flags（backend_parity、task_success、official_benchmark_reproduction、real_world_safety…）全部为 False。

路径 B 还有一条路径 A 没有的纪律：模型看到的观测是脱敏过的（_build_model_visible_observation 会抽掉 privileged state、native dump、solver diagnostics、evaluator truth），而且一旦 pre/post 测量缺失，loop 会走 _finalize_blocked_loop() 记下 blocking_reasons，绝不把缺测量悄悄填成 0。这些机制是路径 B 的灵魂，下两节（6.2 讲八动词 facade，6.3 讲完整 live loop）会逐一拆开。这里你只需记住它和路径 A 的分工。

两条路，一套证据契约

把两条路并排放，差异一目了然：

  • 路径 A（EpisodeRunner）：进程内、薄 Protocol、无 artifact、语义字段留空、为 smoke 与契约回归服务。它回答"管线闭不闭合"。
  • 路径 B（provider live loop）：拉真后端、八动词 facade、产物全 hash 寻址、脱敏观测、缺测量即 blocked、claim_flags 全 False。它回答"这次评测产出了什么级别的证据"。

但两条路的终点是同一个：EpisodeTrace，里面装着 PhysicalStateProjection 与 TaskSemanticState。这不是巧合，而是设计：runtime 层允许有多条产出路径，但证据的形状由 core 锁死，谁都改不了。这正是"OS"的含义——上层应用（怎么跑）可以换，底层契约（产出什么）不能换。

这一节证明了什么 / 还不能证明什么

"存在两条产出 trace 的路径"证明的是 EOS 的 runtime 在工程上把"快速契约回归"和"重证据 live 评测"解耦开了；它不证明任何一次具体评测的结论成立。尤其是：路径 A 的 smoke 用的是 SemanticProxyBackend——一个语义代理，不是真物理，它的 success 只说明管线跑通，绝不是任务能力的证据。哪条路产出的 trace 算"强证据"，取决于 trace 里的 provenance 与 claim boundary 是否齐全，而不取决于它走了哪条代码路。

这一节带走的

EOS 用两条路径产出 trace：路径 A 是 core/runtime/episode_runner.py 里那个朴素的进程内 EpisodeRunner，backend/model 是 Protocol，强制写入六组件与 repo commit，服务于 smoke 与契约回归；路径 B 是 runtime/live_model_loop.py 里的 provider 证据链，拉真后端、产 artifact、缺测量即 blocked。两条路共用 EpisodeTrace / PhysicalStateProjection / TaskSemanticState 这套 core 契约——这就是 runtime 层"可换路径、不可换证据"的核心原则。
