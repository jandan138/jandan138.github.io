不污染 core：契约 vs 领域语义

前两节守的是证据的诚实，这一节守的是架构的诚实。EOS 之所以能号称 domain-agnostic，全靠一条空间纪律：src/embodied_eval_os/core/ 里只放场景中立的契约，绝不放任何领域语义或外来 benchmark 的概念。这条线不是靠口头约定，而是靠一个会让 CI 变红的脚本守着——而且它比文档列的禁词表还要严。

三层放置：契约 / 语义 / 外来概念

EOS 把所有概念分进三个层，每个概念都必须能回答"我属于哪一层"：

  • core = 契约（contracts）：场景中立的抽象。它知道"有一种东西叫 task、有一种东西叫 metric family、有一种东西叫 process primitive"，但不知道任何具体场景的名字。
  • scenario_packs/ = 场景语义：pipette、hazard taxonomy、conveyor 这类领域语义都住在这里，它们 subclass core 的抽象、消费 core 的投影，但不改 core。
  • adapters/ = 外来 benchmark 概念：被导入的 EBench / AutoBio 概念关在这里，作为anti-corruption layer（防腐层）把外部世界翻译成 core 契约。

判断一个概念该进哪层，核心问句是："它是场景中立的契约，还是某个场景/某个 benchmark 的语义？" 前者进 core，后者出 core。

那张禁词表

为了让"出 core"有牙齿，core-boundaries.md §3 列了一张权威的禁词超集（35+ 个），凡是带这些名字的类名或 import，都不许出现在 core：

docs/design/core-boundaries.md §3（节选）
EBench  GenManip  Lift2  Isaac41  IsaacSim  AutoBio  R5A
MJCF  MuJoCo  OpenPI  RDT  EvalClient
Lab  WetLab  Pipette  Centrifuge  TubeRack  Contamination
PCRPlate  VortexMixer
RobotRuntime  EmbodimentRuntime  RobotState  EmbodimentState
CanonicalRobotState  UniversalController  ControlStack
HardwareReady  SafeRobot  URDF  SAPIEN  PhysX  qpos  qvel
（以及 benchmark 专属的 Expert 类）

注意这张表里既有外来 benchmark 名（EBench、GenManip、AutoBio），有引擎/格式名（MuJoCo、MJCF、PhysX、URDF、SAPIEN），有场景语义（Pipette、Centrifuge、Contamination），也有看似中立其实危险的"伪通用"名——比如 UniversalController、CanonicalRobotState、RobotRuntime。它们被禁，是因为"通用机器人状态""通用控制器"这种说法本身就是一种过度承诺（universal robot state 也在 1.2 的 Forbidden Claim Catalog 里）。甚至 qpos / qvel 作为核心 API 名也被禁——它们只能作为 PhysicalStateProjection 里的投影字段值出现，不能升格成 core 的接口名。

check_core_leakage.py：比文档还严

真正在 CI 里站岗的，是 scripts/check_core_leakage.py。它扫描 core/**/*.py 的源文本，命中任一禁词模式（大小写不敏感）就返回非零、让检查失败。值得强调的是：这个脚本比 CLAUDE.md 里那张短表更严——它额外禁掉了 mujoco、isaac_sim、openpi 这些以小写子串形式出现的引擎/模型名：

scripts/check_core_leakage.py（禁词模式，节选）
FORBIDDEN_PATTERNS = [
    ForbiddenPattern("ebench",    _contains_pattern("ebench")),
    ForbiddenPattern("genmanip",  _contains_pattern("genmanip")),
    ForbiddenPattern("isaac_sim", _contains_pattern("isaacsim", "isaac_sim", "isaac sim")),
    ForbiddenPattern("mujoco",    _contains_pattern("mujoco", "mu_joco")),
    ForbiddenPattern("openpi",    _contains_pattern("openpi", "open_pi")),
    ForbiddenPattern("pipette",   _word_pattern("pipette")),
    ForbiddenPattern("contamination", _word_pattern("contamination")),
    # ... ebench / genmanip / lift2 / isaac41 / autobio / r5a / mjcf /
    #     rdt / evalclient / lab / wet_lab / centrifuge / tube_rack /
    #     pcr_plate / vortex_mixer ...
]

两种匹配器分工不同：_contains_pattern 用子串命中（任何地方出现 mujoco 都算），而 _word_pattern 用词边界命中（避免把 lab 误伤进 collaborate 这类无辜的词）。ROOT 写死成 src/embodied_eval_os/core——它只盯核心，scenario_packs 和 adapters 里出现这些词是合法的，那正是它们该待的地方。

为什么 scenario_packs 里写 pipette 反而对

leakage checker 只扫 core/。scenario_packs/scientific_lab/process_primitives/pipette_proxy.py 里满篇 pipette 是完全正确的——领域语义就该住在 pack 里。错的是把 core.PipettePrimitive 写进核心。同一个词，在 pack 里是正确归位，在 core 里是污染。

Core Entry Test：一个概念凭什么进 core

禁词表是"反向"防线（这些名字别进来），还需要一条"正向"准入测试：一个概念能进 core，当且仅当它对以下至少一项有用——

Core Entry Test
对 ≥2 个 scenario packs 有用，或
对 ≥2 个 backend profiles 有用，或
对 ≥2 个 model families 有用，或
今天服务 1 个场景 + 文档化的第二个 roadmap 场景。
否则 → 留在 pack / adapter。

这条测试的精神是："只为一个场景服务的东西，没资格进核心。" 核心的价值正在于复用——能被两个以上场景/后端/模型族共享的抽象，才配当契约。所以 core 允许 TaskSpec / BackendProfile / MetricSpec / InteractionPrimitive / EpisodeTrace 这类名字（它们对所有场景通用），却把 PipettePrimitive 挡在门外（它只对一个场景有用）。下面的部件让你亲手把一堆概念拖进 core / pack / adapter 三个桶——拖错的瞬间，leakage checker 会把它标红。

interactivecore placement：把概念放对地方，leakage checker 替你把关
把 TaskSpec、PipettePrimitive、GenManipRuntime、EpisodeTrace… 拖进 core / scenario_pack / adapter。拖错进 core 的禁词会被标红——这正是 check_core_leakage.py 在 CI 里做的事。

防腐层与依赖方向

adapters 是anti-corruption layer 这个概念（来自领域驱动设计）的字面实践：外部系统（EBench、AutoBio，乃至 MetaSim 这类外部 sim 抽象框架）只能经过 adapter 接入，而且明确规定它们 do not weaken this rule——不许反过来塑造 core 的 API。所以 core.GenManipRuntime、core.Lift2Action、core.EBenchScore 这些写法是非法的；正确的是把它们留在 adapters/ebench/，再翻译成 core 的通用契约（EBench task → 通用 TaskSpec、Lift2 → 一个 EmbodimentSpec、EBench score → 一个 MetricResult）。这一切的底座，是上一节地图里那条绝不反向的依赖箭头：core ← scenario_packs / adapters / backends / model_adapters，core 永不 import 它们。

从 EBench 看 你学过的每一个 EBench 概念，都住在 adapter 里

把你从 EBench 带来的"家当"逐个对号入座，你会发现它们无一进 core：GenManip 的仿真 runtime → adapters/ebench/ 的 runtime config；Lift2 本体与它那套 action 维度 → 一个普通的 EmbodimentSpec + adapter 里的映射；Isaac Sim 4.1 lock-in → 一个 legacy 的 BackendProfile（ebench_genmanip_legacy.yaml，purpose: compatibility_only）；EBench 的 score schema、camera 名字、dataset layout → 全在 adapter。EOS 从 EBench 吸收的是思想（多轴 capability profile、client–server 接口、action chunking、train/test split、诊断报告），那些思想塑造了 core 的契约；而 EBench 的具体实现细节，一个字也没进 core。这就是防腐层的全部意义：要 EBench 的智慧，不要 EBench 的耦合。

这一节的边界声明

"不污染 core" + leakage checker 能保证：核心在静态、名字层面保持 domain-agnostic，没有任何场景或 benchmark 的概念硬编码进契约层。它不能保证：core 的抽象设计得"好"、或某个场景真的能被这套抽象优雅表达——一个名字干净但抽象错位的 core 仍可能是糟糕的。checker 拦的是污染，不是笨拙；架构判断仍要靠 Core Entry Test 和人来做。干净是底线，不是上限。

这一节带走的

把这条空间纪律记牢：概念三层放置——core = 契约、scenario_packs = 场景语义、adapters = 外来概念（防腐层）；core 里禁出现一张 35+ 词的禁词表（含 EBench/MuJoCo/Pipette，乃至伪通用的 UniversalController、core API 名 qpos/qvel）；准入靠 Core Entry Test（≥2 packs / profiles / model families 才配进 core）；而 check_core_leakage.py 在 CI 里站岗，比文档还严（连小写 mujoco / isaac_sim / openpi 都禁），靠的是 core ← 一切 的单向依赖。

Part 1 的三条铁律到此讲完：证据高于能力面、永不过度宣称、不污染 core（外加 no silent fallback 这条贯穿纪律）。下一部分 Part 2 · 后端可组合，我们去拆解第三条铁律的正面——为什么一个后端不能只是一个字符串，而必须被拆成六大组件。
