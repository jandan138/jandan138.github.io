能力矩阵是账本，不是分数

上一节末尾我们埋了一个区分：profile 声明"我有能力做什么"，并不等于"这次 run 真的做到了什么"。这一节把这条缝撑开——它是 Part 2 的收束，也是整本书"差异是证据、不是能力面"主张在后端层的落点。一份能力矩阵看起来像一张漂亮的表，但它是一本账本，记录"这一次到底测到/产出/被 block/失败了什么"；它不是一个可以拿去排名的分数。

两层：registry vs readiness ledger

EOS 刻意把后端能力分成两层，永远不让它们塌缩成一个：

  • runtime capability registry（能力注册表）——静态声明。这就是 2.2 的 BackendProfile：它写明这个后端打算/有能力支持哪些组件、每格的 CapabilityTier 是什么。它是一份菜单，在 run 开始之前就存在。
  • backend readiness ledger（就绪账本）——这一次实测。它记录在这一条具体的 run 里，每根轴到底发生了什么：测到了？近似测到了？只读？被 block 了？失败了？它是这一餐实际端上桌的东西，在 run 之后才填得出来。

菜单上写着"供应龙虾"，不代表今晚你桌上有龙虾——也许厨房缺货（blocked_provider_unavailable），也许这道菜这次没点（not_evaluated）。registry 是前者，ledger 是后者。把两者混为一谈，正是过度宣称的温床。

从评测科学 看 声明的能力 ≠ 兑现的证据

这正是 reproducibility 文献反复敲打的点。Henderson 等人（"Deep RL that Matters", AAAI 2018）证明：同一份"能跑"的声明，换个 seed、换个实现细节，结果可以天差地别——所以一份能力声明本身不是证据，每一次 run 的实测才是。EOS 的 readiness ledger 就是把"这一次到底兑现了多少"逐轴记下来，而不是停留在 registry 的"我支持"。这和 datasheet / model card 把"声明"与"实测局限"分栏列写是同一种纪律。

轴级状态：一格不止"行/不行"

账本里每一根轴的状态，不是布尔，而是落在一组细粒度的词上（backend-composability.md 给出的 axis-level status）：

status含义
exact这根轴被精确测到/产出。
approximate测到了，但是近似值。
partial只产出了一部分（如端点采样，缺逐步数据）。
read_only可读不可写。
opaque_only只有不透明 dump，没有解析后的结构化证据。
unsupported这根轴根本不提供。
blocked本应有、这次却没被产出/无法兑现——显式记 block + reason，不填 0。

你已经在 2.2 的 mujoco_autobio.yaml 里见过活的账本：它的 interaction_dynamics 表里 native_contact_pairs 是 partial（"端点样本含原生 geom pair 与距离证据，但完整逐步/子步接触 pair 包未 materialize"），而 contact_force_vectors / solver_constraints 等是 blocked（各附 reason）。注意这里的纪律：缺接触力向量是一个 coverage limit / blocker，不是 false negative，绝不写成 0.0。这正是 No Silent Fallback 政策（1.3）在后端账本上的体现：缺证据要变成显式状态，而不是一个看起来无害的零。

一张支持矩阵不蕴含什么

这是本节的核心，也是 EOS 反复强调的一句话。哪怕一份支持矩阵满屏 native / exact，它都不蕴含下面这些（backend-composability.md 原文）：

"A simulator support matrix … does not imply task success, backend equivalence, trajectory parity, contact-force parity, render parity, sensor calibration, official benchmark reproduction, or real-world safety."

逐条拆开它否定了什么：

  • ≠ task success：后端支持某能力，不代表模型在这个后端上把任务做成了。
  • ≠ backend equivalence / trajectory parity / contact-force parity：两个后端各自都 native，不代表它们轨迹一致、接触力一致——上一节已说明接触是 NCP，各引擎松弛方式不同，本就会分叉。
  • ≠ render parity / sensor calibration：两边都能出 RGB，不代表像素可比、传感器标定一致。
  • ≠ official benchmark reproduction：能跑通一个兼容 smoke，不等于复现了官方 benchmark（这正是 mujoco_autobio.yaml 把 faithful_claim_requires 列成 official_assets / official_plugins / external_commit / claim_boundary_review 的原因）。
  • ≠ real-world safety：仿真里的危险轴是 simulator-only hazard，永远不等于真实世界安全认证。

换句话说：能力账本回答的是"这次我们到底有哪些证据、各处于什么状态"，它不回答"谁更强""谁等价""谁复现了谁"。把账本读成排行榜，是对它最根本的误用。

动手：读一张账本，分清 registry 与 readiness

下面这个部件把两层叠在一起：左边是 registry（声明的 tier），右边是这一次 run 的 readiness（逐轴 status）。拨动它，体会"声明 native"与"这次 exact / partial / blocked"是两件不同的事。

interactivecapability ledger：registry（声明）对照 readiness（这次实测）的逐轴 status
逐轴查看 exact / approximate / partial / read_only / opaque_only / unsupported / blocked。重点感受：一根 registry 标 native 的轴，readiness 里完全可能是 blocked——缺证据被记成显式 block，而不是被偷偷填成 0 或 success。
能力矩阵能证明什么、不能证明什么

一份 EOS 能力矩阵能证明的：在这一次 run 里，每根能力轴各自处于什么状态（exact / approximate / partial / read_only / opaque_only / unsupported / blocked），以及每个 blocked 背后的显式 reason。它不能证明：任务成功、后端等价、轨迹 parity、接触力 parity、渲染 parity、传感器标定一致、官方 benchmark 复现、或真实世界安全。账本是证据的逐轴记账，不是分数、不是排行、不是 parity 声明。任何把这张表压成一个数字拿去比大小的做法，都越过了它的 claim boundary。

这一节带走的

三点：（1）能力分两层——registry（profile 静态声明的 tier，菜单）与 readiness ledger（这一次 run 逐轴实测的 status，端上桌的东西），绝不塌缩成一个；（2）轴级状态是细粒度的 exact / approximate / partial / read_only / opaque_only / unsupported / blocked，缺证据记 blocked+reason 而非填 0；（3）一张支持矩阵不蕴含 task success / backend equivalence / trajectory·contact·render parity / sensor calibration / official reproduction / real-world safety——它是账本，不是分数。

Part 2 到此收束：你已经能把任何"后端"拆成六组件、写成一份带 tier 的 profile、并把它的能力读成一本逐轴记账的账本。下一部分（Part 3）我们转向 EOS 的另一根脊梁——L0–L6 分层与三层状态，看证据是怎么从原始测量一路归一化、最终沉淀成 EpisodeTrace 的。
