一个后端不是一个字符串：六大组件

在 EBench 里，"后端"是一个名字：Isaac Sim。你说"我在 Isaac 上跑"，所有人都懂——因为那套栈是焊死的。可一旦你想问"这个失败是渲染器的锅还是物理的锅""换个渲染器结果还成不成立""把 PhysX 换成 MuJoCo physics、其它都不变、模型还行不行"，那个单一的字符串就立刻不够用了。这一节我们把"后端"这个词拆开——拆成 EOS 强制记录的六个组件。这是铁律三，也是后面整个 Part 2 的地基。

为什么"一个名字"会骗你

设想你看到一行实验结论："模型在 Isaac 上 success rate 72%，在 MuJoCo 上掉到 41%。" 这句话听起来像个发现，其实什么都没说清。Isaac 和 MuJoCo 之间，同时变了一大堆东西：物理求解器不同、渲染管线不同（RTX 光追 vs 简易 OpenGL）、传感器噪声模型不同、控制接口的语义不同、连场景资产的导入路径都可能不同。掉的那 31 个百分点，到底是因为模型看不惯新渲染器的图像，还是因为新物理引擎下接触力不一样导致抓取打滑？你无法归因。

这正是 EOS 的核心主张之一：差异是证据，不是能力面。但一个差异要能当证据用，前提是你能说清"到底是哪个变量变了"。把后端压成一个字符串，等于把所有自变量绑在一起一起拧——这在评测科学里是最基本的混淆（confounding）。EOS 的解法简单而严厉：永远不许把后端只描述成 Isaac / MuJoCo / Genesis，而要把它拆成六个独立可换的组件。

从物理后端 看 真实引擎本来就是"组件束"

这个拆分不是 EOS 发明的人造概念——真实引擎本身就是一捆组件。Isaac Sim 是 USD 场景描述 + PhysX 物理 + RTX 光追渲染 + 一套传感器/相机模型 + articulation controller，这些本来就是可以各自替换的层（Isaac Lab 现在甚至能在同一个壳里换 PhysX / Warp / Newton / MuJoCo 物理）。MuJoCo 的物理求解器、它的 OpenGL 渲染器、它的 actuator 模型也是三件不同的东西。EOS 只是拒绝把这捆东西重新打包成一个名字，然后假装它是原子的。

六个组件，逐一定义

下面是 backend-composability.md 给出的六个组件的权威定义与例子。请把这张表当作 Part 2 的字典——后面讲 BackendProfile 数据类（2.2）、讲具体引擎（2.3）、讲能力账本（2.4）都直接复用这六个名字。

组件定义（原文）例子
platformthe integration environment or simulator shellIsaac Sim; MuJoCo; Genesis; custom split backend; real robot runtime
physicsthe source of physical transition dynamicsPhysX; Newton; MuJoCo physics; Genesis physics; real world; reduced semantic physics
rendererthe source of image-like observationsIsaac RTX; Blender Cycles; MuJoCo renderer; Genesis renderer; real camera; offline rerenderer
sensorsthe source of sensor readingsRGB; depth; segmentation; force/torque; tactile; proprioception; instrument logs
controlthe execution interface for actionsjoint action; ee-delta; action chunk; skill command; ROS control; articulation controller
process runtimethe source of scenario-specific semantic state transitionsreduced liquid model; device state machine; hazard event generator; lab pipette primitive; conveyor; terrain transition

注意最后一个 process runtime 最容易被忽略，却最体现 EOS 的野心。它是"场景专属语义状态转移的来源"——比如"液体被吸进移液器后体积怎么变""危险事件什么时候触发""传送带把零件送到哪"。物理引擎管的是刚体怎么动，process runtime 管的是场景语义怎么演化。这两者必须分开，因为一个 reduced liquid model（语义代理）绝不等于真实流体力学——这条 claim boundary 会在 scientific_lab pack 里反复出现。

拆开能买到什么：五种"只换一个变量"的对比

把后端拆成六个可独立替换的组件，立刻解锁了一组干净的对照实验。每一种都是"固定其它一切，只动一个组件"，从而把原本纠缠在一起的归因问题拆开：

  • 同 rollout 换 renderer：同一条动作轨迹、同一套物理，只换渲染器——分离 视觉泛化（模型认不认得新画风）和动力学。
  • 同 task 换 physics：任务规格、度量规格都钉死，只换物理引擎——分离 simulator artifact（求解器松弛带来的接触差异）和模型真本事。
  • 同 task 换 embodiment：换本体，看模型对新关节布局的鲁棒性。
  • 同 trace 换 evaluator：同一条 EpisodeTrace，换不同评判器——分离"模型表现"和"我们怎么打分"。
  • 同 scene 换 sensor noise：只动传感器，看 renderer-dependent failure 还是 physics-dependent failure。

这五种对照，每一种都因为"只有一个自变量在动"而具备归因能力。这就是组件拆分的全部回报：它把"Isaac vs MuJoCo 整体掉了 31%"这种不可归因的观察，变成"在任务与度量固定下，PhysX 与 MuJoCo physics 的接触差异导致抓取阶段分叉"这种可归因的证据。

跨后端实验的硬约束：只改一个组件

EOS 对跨后端实验有一条强制措辞纪律。不要写"Compare Isaac vs MuJoCo"——那句话里至少六个变量同时变了，结论无法归因。要写"Compare PhysX vs MuJoCo physics while keeping task spec and metric spec fixed"。换句话说：跨后端对比必须是组件级的，而不是平台级的，并且要显式说明哪五个组件被钉死、哪一个被替换。一个改了多个组件的"对比"在 EOS 里不被当作有效证据。

从 EBench 看 为什么 EBench 不需要这条铁律

EBench 完全可以只说"Isaac"，因为它的后端是焊死的：Isaac Sim 4.1 + Lift2 本体 + GenManip server + 一套固定的 action 维度，绑成一个整体，从不拆开替换。在那个世界里，"后端"确实就是一个字符串，而且够用。但这正是 EOS 要超越的局限——一旦你想跨场景、跨引擎、跨本体地评测，并且想把差异当证据，那个焊死的整体就必须被拆成可组合的组件。EBench 的这套栈在 EOS 里被收进 ebench_genmanip_legacy.yaml（purpose: compatibility_only），作为一个组件已经被拆开标注的 legacy profile。

动手：组一个后端，看它能做什么对比

把六个组件组合成一个 profile 是一回事，理解"这个组合能支持哪些对照实验、不能支持哪些"是另一回事。下面这个部件让你亲手拼装组件，并立刻看到由此解锁（或仍然缺失）的对比实验。

interactivebackend composer：六组件 → profile → 它能/不能支持的对比
逐一选择 platform / physics / renderer / sensors / control / process runtime，下方会算出你能跑哪些"只改一个变量"的对照实验。试试只改 physics 保持其它不变——看它点亮"physics 归因"，而同时改 renderer + physics 会让对比失去归因能力。

这一节带走的

三点：（1）"后端"在 EOS 里不是一个字符串，而是 platform / physics / renderer / sensors / control / process runtime 六个独立可换的组件——这是铁律三；（2）拆开的回报是可归因：你能跑"只换一个变量"的对照，分离视觉泛化与动力学、simulator artifact 与模型本事；（3）跨后端实验必须只改一个组件，措辞要落到组件级（"PhysX vs MuJoCo physics, task+metric fixed"），不许停在平台级（"Isaac vs MuJoCo"）。
