Backend profile 与 capability tier

上一节我们在概念上把后端拆成了六个组件。这一节要回答两个很实在的问题：这"一束组件"在代码里到底长什么样？以及——怎么让它诚实地说出自己每一格能做到几分？我们会从一个具体的困惑出发，一步步把 BackendProfile 搭起来，不急着丢代码。

先问一个问题：两个 0.6 能比吗？

设想两个团队都跑了同一个抓取任务，都来报喜：「我在 MuJoCo 上跑的，success rate 0.6。」听起来可以直接比——0.6 平 0.6。但只要多问几句就会发现地基是虚的：

  • 是 MuJoCo 哪个版本？3.1 和 3.3 的接触求解器行为可以不一样。
  • 渲染用的是 MuJoCo 自带的 OpenGL，还是接了 Blender？模型看到的图像完全是两回事。
  • 有没有 force/torque 传感器？还是只有关节角？
  • 动作是关节位置控制，还是末端 delta？
  • 那个"液体"是真算的，还是一个简化的语义代理？

换句话说，「在 MuJoCo 上」这五个字什么都没说清。两个 0.6 很可能是在两套不同的世界里得到的，根本不可比。这正是 2.1 那条铁律的代价：既然后端是一束组件，那"我在某后端上跑的"这句话，就必须升级成一份写明六格配置的规格单，并且钉在每一个结果旁边。

一个好用的类比

BackendProfile 就是后端的配料表 / 规格铭牌。你买一包食品，包装上印着配料、产地、保质期——不是为了好看，而是为了让"这包东西到底是什么"可追溯、可比较、可追责。EOS 给每个评测结果配的，就是这样一张铭牌：它不保证好吃，但它保证你知道自己吃的是什么。

从一个字符串，到一束有名有姓的组件

最偷懒的写法是 backend = "mujoco"——一个字符串。但字符串塞不下版本、塞不下"这一格只是代理"、塞不下"这一格根本没有"。所以 EOS 先给单个组件一个专门的数据类型，叫 ComponentProfile。先别管完整代码，看一个最小的例子——描述"physics 这一格"：

一个 ComponentProfile（示意）
ComponentProfile(
    name="mujoco",            # 这一格用什么
    component_type="physics", # 它是六格里的哪一格
    version="3.3.0",          # 版本是一等公民
    capabilities={            # 这一格各项能力，分别几分
        "rigid_body": "native",
        "articulation": "native",
        "contact": "native",
    },
)

逐字段读一遍，意图就很清楚了：

  • name + component_type：这一格是什么、属于六格里的哪一格。
  • version：可选，但一旦填上就被当真。"PhysX 4.1"和"PhysX 5.0"是两个不同的 ComponentProfile——这就是为什么 2.3 反复强调版本。
  • capabilities：一个小字典，把这一格细分到具体能力（刚体、关节、接触……），每项单独给一个保真度。后面 CapabilityTier 这一节就是讲这里填的值。

关键转变是：组件不再是一个裸名字，而是一个有名有姓、带版本、逐项标注保真度的小对象。六格各来一个这样的对象，凑起来就是一个完整后端。

把六个组件装进一个 BackendProfile

BackendProfile 就是"把六格 ComponentProfile 装进同一张铭牌"的容器。现在再看真实代码，就不再是天书了（真实文件，逐字未删）：

src/embodied_eval_os/core/specs/backend_profile.py
class CapabilityTier(str, Enum):
    """Capability fidelity declaration for a backend component."""

    NATIVE = "native"
    REDUCED = "reduced"
    SEMANTIC_PROXY = "semantic_proxy"
    EMULATED = "emulated"
    UNSUPPORTED = "unsupported"


@dataclass(frozen=True)
class ComponentProfile:
    """A composable backend component: physics, renderer, sensor, control, etc."""

    name: str
    component_type: str
    version: str | None = None
    capabilities: dict[str, CapabilityTier | str] = field(default_factory=dict)
    metadata: dict[str, Any] = field(default_factory=dict)


@dataclass(frozen=True)
class BackendProfile:
    profile_id: str
    platform: ComponentProfile
    physics: ComponentProfile | None = None
    renderer: ComponentProfile | None = None
    sensors: list[ComponentProfile] = field(default_factory=list)
    control: ComponentProfile | None = None
    process_runtime: ComponentProfile | None = None
    metadata: dict[str, Any] = field(default_factory=dict)

    def component_summary(self) -> dict[str, str | None]:
        return {
            "platform": self.platform.name,
            "physics": self.physics.name if self.physics else None,
            "renderer": self.renderer.name if self.renderer else None,
            "control": self.control.name if self.control else None,
            "process_runtime": self.process_runtime.name if self.process_runtime else None,
        }

有了前面的铺垫，三个设计选择现在一眼就懂：

  • platform 是唯一必填项，其余五格都允许是 None。这本身是一种诚实：一个只做核心 smoke 的后端可以没有真渲染器、没有 process runtime，而 None 明确说"这里什么都没有"，而不是含糊带过。
  • sensors 是个列表（其余五格是单个组件）。因为一个后端可以同时挂 RGB、深度、force/torque 好几路传感，单数装不下。
  • component_summary() 把六格压成一个扁平字典，专门喂给 trace 元数据和报告。注意它没有展开 sensors 列表——列表单独处理。
三个 Python 词，别被吓到

代码里有几个修饰词，对不熟 Python dataclass 的读者可能扎眼，但意思都很朴素：

@dataclass＝"自动生成构造函数的小数据容器"，你只管声明有哪些字段。frozen=True＝"造好就封存不可改"，像一份盖了章的公证文件；正因为不可改，它才能被哈希（当成唯一指纹）。field(default_factory=dict)＝"这个字段默认是个空字典/空列表"，只是给默认值的标准写法。

为什么非要"封存+可哈希"？因为一条 EpisodeTrace 要把后端身份当证据指纹记下来（backend_profile_id + backend_components）。封存保证了：后端身份在一次 run 里不会中途漂移——你不能跑到一半偷偷把 physics 从 proxy 换成 native 再来邀功。

CapabilityTier：把"我能做到几分"写进合同

现在回到那个 capabilities 字典里填的值。CapabilityTier 是这套设计里最体现 EOS 哲学的部分：一个组件不是"支持 / 不支持"的布尔，而是落在五个保真度档位上。

tier含义什么时候选它
NATIVE引擎原生、全保真地提供这个能力。MuJoCo 原生算的刚体接触。
REDUCED提供，但是降级 / 简化版本。为了快，关掉了某些精度。
SEMANTIC_PROXY只是语义代理——用简化模型近似该现象，不是真实物理。reduced liquid model 估液量。
EMULATED由非原生路径模拟出来。用脚本/别的量推算出来的。
UNSUPPORTED这个组件根本不提供该能力。dummy 后端不出图像。

核心在于：tier 是一份声明，而且这份声明在评测还没开始时就已经写下了。声明 SEMANTIC_PROXY，等于提前把 claim boundary 钉死——任何基于这个组件的结论，都不许悄悄升格成"真实物理"的结论。下面这个部件让你亲手感受这件事：选一个组件，再在保真度阶梯上挪动，看它立刻把"你可以说什么、不能说什么"卡在哪里。

interactiveCapabilityTier → 可以说什么 / 不能说什么
先点上方组件（physics / renderer / sensors / process_runtime），再在阶梯上选一档。注意：tier 一降，"可以说"的话立刻缩水，"不能说"的红线立刻收紧——保真度声明就是 claim boundary。
从评测科学 看 tier 就是写在合同里的 construct boundary

测量科学里讲 construct validity：你的指标必须真测到你声称的构念。CapabilityTier 把这条纪律前置到后端声明阶段——还没开始评测，profile 就已经写明"我的 physics 是 semantic_proxy"，于是任何下游报告都不能把这个代理的输出当成真实流体力学证据。这和 Model Cards（Mitchell et al., FAT* 2019）的精神一致：把局限写进规格，而不是埋在脚注里事后辩解。

别搞混：三套"状态词"各管一段

这是这一节最容易绕晕的地方，所以单独拎出来讲清楚。EOS 里会出现三套看起来都像"状态"的词，它们分属不同阶段、各管一段，不能混用：

词汇谁在用取值回答的问题
CapabilityTier组件级·声明阶段native / reduced / semantic_proxy / emulated / unsupported"这一格的保真度是几分？"
axis-level status证据轴级·实测阶段exact / approximate / partial / read_only / opaque_only / unsupported / blocked"这一轴证据这次到底拿到没拿到？"（详见 2.4）
claim_boundaryprofile / trace 级·自由文本一句话"基于以上，这份证据能/不能主张什么？"

一句话记牢三者的关系：CapabilityTier 是声明能做到几分（菜单），axis-level status 是实测这次拿到几分（这一餐实际端上桌的），claim_boundary 是把前两者翻译成人话的边界声明。 你会在 capabilities 字典里同时看到 tier 风格的值（native）和 axis 风格的值（blocked）——这是被允许的（字段类型就是 CapabilityTier | str），但写的时候要清楚自己在表达哪一层。

最小 profile：dummy_backend.yaml 全文

profile 在仓库里以 YAML 落盘，顶层 key 一一对应 dataclass 字段：profile_id / platform / physics / renderer / sensors（列表）/ control / process_runtime / metadata。最小的代表性 profile 是核心 smoke 专用的这一份——它故意"什么都不做真的"，正好用来逐 key 解释：

configs/backend_profiles/dummy_backend.yaml
profile_id: dummy_backend
platform:
  name: dummy_backend
  component_type: platform
physics:
  name: semantic_proxy
  component_type: physics
  capabilities:
    rigid_body: semantic_proxy
    articulation: semantic_proxy
renderer:
  name: none
  component_type: renderer
  capabilities:
    rgb: unsupported
sensors:
  - name: none
    component_type: sensor
control:
  name: direct_delta
  component_type: control
process_runtime:
  name: none
  component_type: process_runtime
metadata:
  role: core_smoke_only
  claim_boundary: no simulator fidelity or benchmark compatibility claim

逐 key 读这份"诚实到极致"的最小 profile：

  • platform.name: dummy_backend——不是任何真实仿真器，只是一个壳。
  • physics 的两条能力 rigid_body / articulation 都标 semantic_proxy：它不算真实动力学，只是个语义近似。这一行直接决定了所有基于它的结果的 claim boundary。
  • renderer.capabilities.rgb: unsupported——明说"我不出图像"。它没有偷偷返回一张黑图假装成功，而是显式声明不支持。这正是 no-silent-fallback 在后端声明层的体现。
  • sensors 是个只有一个 name: none 的列表，control 是 direct_delta（直接把动作当成 delta 应用），process_runtime.name: none——没有场景语义状态机。
  • metadata 把话挑明：role: core_smoke_only，claim_boundary: no simulator fidelity or benchmark compatibility claim。这个 profile 存在的全部意义，就是让 examples/run_smoke.py 能在零仿真器依赖下跑通整条 trace 管线——pyproject 的运行时依赖只有 pyyaml 和 typing-extensions，引擎都在 adapter 侧。
从物理后端 看 一份"全是 proxy"的 profile 仍然是合法后端

从真实引擎的视角看，dummy_backend 像个笑话——它什么物理都不算。但在 EOS 的证据框架里它完全合法：它诚实地声明了自己每一格的保真度，因此它产出的 trace 仍是有效证据——只不过证据的边界被 profile 卡得死死的。这比一个偷偷返回 success=true 的"高保真"假后端要强得多。诚实的代理 > 不诚实的逼真。

一条 profile 的"来回旅程"

把上面拼起来，你就能看清一份 profile 从代码到证据的完整旅程——这也是把前面所有零件串成一根线的好办法：

BackendProfile 的来回旅程
① 构造：六个 ComponentProfile 装进一个 BackendProfile（platform 必填，其余可 None）
        ↓  frozen=True → 封存、可哈希
② 落盘：序列化成 configs/backend_profiles/*.yaml（顶层 key 对齐字段）
        ↓
③ 压扁：component_summary() → {platform, physics, renderer, control, process_runtime}
        ↓
④ 入证：写进每条 EpisodeTrace 的 backend_profile_id + backend_components
        ↓
⑤ 约束：metadata.claim_boundary 跟着结果一起走，谁读结果谁就读到边界

注意第④步：后端身份不是"评测时顺手记一笔"的附属信息，而是被钉进每条 trace 的一等证据。这就是为什么前面要那么在意"封存、可哈希"——只有不可变的指纹，才配当证据。

对照：mujoco_autobio.yaml 富在哪

把 dummy 放在一边，看 configs/backend_profiles/mujoco_autobio.yaml 这份"富"profile，能看清同一套 schema 怎么承载真实运行时的全部复杂度：

  • 带版本的真物理：physics.name: mujoco，version: "3.3.0"，rigid_body / articulation / contact 全是 native——真实引擎、真实接触求解。
  • 多个传感器：sensors 列表里有 autobio_rgb_cameras（rgb native）和 autobio_proprioception（joint_state native），印证了"sensors 是列表"的设计。
  • 一张 interaction_dynamics 子表，大量标 blocked：contact_force_vectors、contact_force_summary、solver_constraints、plugin_or_process_forces……几乎全是 blocked，每一格都附 reason。⚠ 注意：这里的 blocked 是上一节讲的axis-level status（实测没拿到这一轴证据），不是 CapabilityTier——别和 physics: native 那种"声明"混为一谈。它说的不是"测出来是 0"，而是"这一轴的证据这次没被产出，所以显式 block"——No Silent Fallback 的教科书示范。
  • 富 metadata：external_benchmark: AutoBio、anti_corruption_layer: adapters/autobio、reproduction_mode: faithful_runtime_when_requirements_met，外加一整段 limitations（"requires external AutoBio repository…""does not make AutoBio or MuJoCo a core dependency""does not imply official benchmark reproduction without provenance review"）和 faithful_claim_requires（official_assets / official_plugins / external_commit / claim_boundary_review）。

同一个 schema，从"全 proxy 的 smoke"到"真 MuJoCo + 一长串显式 blocked 轴 + faithful 复现的前置条件清单"，跨度很大却毫不变形——这正是把后端拆成组件束、每格独立定级带来的表达力。

profile 声明 ≠ 结果保证

一份 BackendProfile 声明的是"我打算 / 有能力提供什么保真度"，不是"这次 run 真的产出了什么、真的成功了什么"。physics: native 不等于这条 trace 里抓取成功；interaction_dynamics 里十条全 native 也不等于后端等价或 benchmark 复现。声明（registry）与实测（readiness ledger）是两层，绝不能混为一谈。这条区分是 2.4 整节的主题——profile 是菜单，账本才是这一餐实际端上桌的。

这一节带走的

四点：（1）「在某后端上跑的」必须升级成一份写明六格配置的规格铭牌，否则两个 0.6 不可比；（2）铭牌落进代码是两个 frozen dataclass——ComponentProfile（name + type + version + capabilities + metadata）描述单格，BackendProfile（platform 必填、sensors 是列表、其余可 None）装六格，不可变因此可当证据指纹钉进 trace；（3）CapabilityTier（NATIVE / REDUCED / SEMANTIC_PROXY / EMULATED / UNSUPPORTED）把每格能力诚实定级，把 claim boundary 前置到声明阶段；（4）三套状态词各管一段——CapabilityTier 声明保真度、axis-level status 记实测有没有拿到、claim_boundary 把边界写成人话。

下一节，我们带着这套词汇走出去，逐一看真实引擎——Isaac / MuJoCo / Genesis / PyBullet / Newton——把它们各自映射到这六个组件上。
