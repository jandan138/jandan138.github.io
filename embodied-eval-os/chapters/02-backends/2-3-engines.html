引擎众生相：Isaac / MuJoCo / Genesis / PyBullet / Newton

现在你有了一套词汇：六个组件、五个 capability tier、一份可校验的 profile。这一节我们带着这套词汇走出去，看真实世界里那几个常被点名的引擎到底是什么——并且拒绝把它们当成一个个原子名字。Isaac、MuJoCo、Genesis、PyBullet、Newton，每一个其实都是一捆组件。看清这一点，你才会明白为什么 EOS 的 core 对它们一个都不依赖。

从物理后端 看 读这一节的正确姿势

下面每一个"引擎"都不是一个点，而是一束组件。读的时候请不停地把它拆回 platform / physics / renderer / sensors / control / process runtime——这正是 2.1 教你的反射动作。当有人说"我们支持 Genesis"，你应该立刻追问："Genesis 的哪个 physics solver？哪个 renderer？哪种 control 接口？" 一个引擎名字回答不了这些问题。

Isaac：一个名字下其实有四样东西

Isaac 是最容易被说成"一个后端"、却最该被拆开的例子。至少要分清四个不同层次的东西：

  • Isaac Sim：跑在 NVIDIA Omniverse 上的全功能仿真器——platform。它的世界用 USD 描述，物理来自 PhysX，渲染来自 RTX 光追。
  • Isaac Lab：架在 Isaac Sim 之上的轻量机器人学习框架，取代了老的 Isaac Gym / Orbit。关键是：它现在能在同一个壳里换多种物理后端——PhysX / Warp / Newton / MuJoCo。也就是说 platform 固定为 Isaac Lab 时，physics 仍是可换的组件。
  • PhysX：physics 组件本身。
  • RTX：renderer 组件本身。

把这四样塞进一个"Isaac"，就丢掉了 EOS 最需要的归因力。在 EOS 里你不会写"backend = Isaac"，而会写一份 profile：platform: isaac_lab / physics: physx / renderer: rtx / …（参见 isaac_physx_rtx.yaml、以及实验性的 isaac_newton_experimental.yaml）。

从 EBench 看 EBench 用的是 Isaac Sim 4.1

你在 EBench 教程里跑的那套，platform 是 Isaac Sim 4.1——早于 2025 年才 GA 的 Isaac Sim 5.0 / Isaac Lab 2.2。这不是细节强迫症：版本是 ComponentProfile 的一等字段，因为不同版本的 PhysX、不同版本的 USD 管线，行为可以不一样。EOS 把 EBench 这套 Isaac 4.1 栈固定在 ebench_genmanip_legacy.yaml（purpose: compatibility_only）里，正是为了把"我们是在那个具体版本上做的兼容"这件事钉死，而不是含糊地说"在 Isaac 上"。

MuJoCo：优化式软接触 + 两条 GPU 路径

MuJoCo（Google DeepMind）的招牌是 optimization-based 软接触——它把接触当成一个优化问题求解，因此数值上格外稳定、可微友好，是机器人学习社区的常用基线。围绕它有两条重要的 GPU 路径，别搞混：

  • MJX：MuJoCo 3 的 JAX 实现，把仿真搬上 GPU 做大规模并行。
  • MuJoCo Warp：与 NVIDIA 合作、基于 Warp 的路径，它正是喂给 Newton 的那一环（见下文）。

在 EOS 里，MuJoCo 是迄今最"实"的一条 live 路径：RPF-7A 是第一个 fresh 的 MuJoCo 3.3.0 live provider（status: executed_pass，产出真实 motion_delta）。它对应的 profile 就是你在上一节读过的 mujoco_autobio.yaml——physics native、但 interaction_dynamics 那张表里接触力向量等轴大量 blocked。

Genesis：多 solver 跨材质，速度数字很夸张

Genesis（genesis-embodied-ai，2024-12 首发）是一个纯 Python 的物理平台，亮点是多 solver 跨材质耦合：Rigid / MPM / SPH / FEM / PBD / Stable Fluid 等多个求解器可以在同一场景里耦合，对应刚体、颗粒、流体、可变形体等不同材质。它最出圈的是性能宣称：在单张 RTX 4090 上、Franka 机械臂场景达到 43M FPS，约合 430,000× 实时，并宣称比 Isaac Gym 快 10–80×。

但这里有一个常被夸大的点必须按实写：在 v0.3 时，Genesis 只有 MPM + Tool solver 可微——不是全可微。EOS 用的是 Genesis 0.4.4，对应 profile genesis_native.yaml。RPF-9 把 PyBullet 和 Genesis 0.4.4 都做成了 live provider，正是为了证明 EOS 的 provider facade"不止 MuJoCo"。

PyBullet：轻量基线

PyBullet（Erwin Coumans，2017 年作为 Bullet 的 Python 绑定引入，Zlib 许可）是经典的轻量级开源后端：安装简单、Python 友好、跨平台，长期扮演机器人仿真的"标准轻量基线"角色。它不追求最高保真，但胜在低门槛、易复现——这让它成为 EOS 做 conformance 和 live model loop 的理想起点。RPF-10 的 live model loop 就是 PyBullet + scripted_demonstrator（privileged_state_visible_to_model: false，standard_model_score: null）。

Newton：2026 仍是 BETA，不是 1.0

NVIDIA Newton 是较新的开源物理引擎，由 NVIDIA + Google DeepMind + Disney 联合发起，托管在 Linux Foundation，Apache-2.0，构建于 Warp + OpenUSD 之上，并集成 MuJoCo Warp。请准确表述其成熟度：到 2026 年它仍处于 beta，不是 1.0——2025-09-29 在 CoRL 以 beta 形态发布，运行在 Isaac Lab 之内。所以在 EOS 里它对应的是 experimental profile（isaac_newton_experimental.yaml），名字里就带着"实验性"的诚实。

从物理后端 看 为什么这些引擎在同任务上会给出不同结果

别期望换个引擎结果就一致——这是物理引擎的现实，不是 bug。接触是非光滑互补问题（NCP），每个引擎为了速度和稳定性各自做不同的松弛：把摩擦锥线性化成 LCP、把硬互补软化成允许少量穿透。证据是现成的：SimBenchmark（RaiSim/Bullet/ODE/MuJoCo/DART）显示各引擎表现高度 task-dependent；cloth manipulation benchmark 发现 quasi-static 任务大家误差都低，但 dynamic 任务没有任何引擎能精确匹配（MuJoCo 相对最好）。这正是 EOS 不去声称"backend parity"、而把跨引擎差异当成需要记账的证据的根本原因（Part 7 会把这件事做到极致）。

EOS 的 core 一个引擎都不依赖

这一节点了五个重量级引擎，但有一件事要说清楚：EmbodiedEval OS 的 core 对它们没有任何依赖。pyproject.toml 里 embodied-eval-os 的运行时依赖只有 pyyaml 和 typing-extensions——所有仿真引擎都是 adapter 侧的可选依赖。你可以 pip install 整个 EOS、跑通 examples/run_smoke.py（走 dummy_backend 的 SemanticProxyBackend）、读一条完整 trace，而不装任何一个引擎。引擎是插上来的，不是焊死的——这就是"backend-composable"在依赖图上的字面意思。

这一节带走的

三点：（1）每个"引擎"都是一束组件——Isaac 至少分 Isaac Sim / Isaac Lab / PhysX / RTX 四层，EBench 用的是 Isaac Sim 4.1；MuJoCo 是优化式软接触 + MJX/Warp 两条 GPU 路；Genesis 0.4.4 多 solver、43M FPS、v0.3 仅 MPM+Tool 可微；PyBullet 是轻量 Zlib 基线；Newton 在 2026 仍是 beta、基于 Warp+OpenUSD、集成 MuJoCo Warp；（2）同任务跨引擎结果本就不同（接触是 NCP，各自松弛），所以差异要记账、不声称 parity；（3）EOS 的 core 运行时只依赖 pyyaml + typing-extensions，引擎全在 adapter 侧可选。
