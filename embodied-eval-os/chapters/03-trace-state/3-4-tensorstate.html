为什么不是一个裸 TensorState

这一部分一路在加结构：七层脊柱、三层状态、十几个字段的 EpisodeTrace。一个合理的反问会冒出来——这是不是把简单的事搞复杂了？仿真器不就吐一个状态张量吗，拿来比一比不就行了？MetaSim 的 TensorState 不正是这么干的吗？这一节正面回答这个反问：为什么 EOS 拒绝把一个裸张量当作评测真相。核心只有一句——同样的形状，证明不了任何东西。

同形状，七重沉默

设想两个后端各吐出一个 shape 完全相同的状态张量：同样的维度、同样的长度，逐元素都能对齐相减。看起来不能更适合比较了。但这个「同形状」沉默地没有保证以下七件事中的任何一件——而少了它们，逐元素的差值毫无意义：

  1. component inventory（组件清单）——两边装的是同一批物体/机器人/相机吗？还是一边多了一个夹爪？
  2. joint / body / actuator / contact ordering（排序）——第 7 个数在 A 里是 elbow，在 B 里会不会是 wrist？
  3. comparable frames / units / sign / force families（坐标系·单位·正负·力家族）——同样是「力」，一边是 N 一边是 N·m？一边是接触求解力，一边是约束保持力？
  4. writable velocity-solver state（可写的速度求解器状态）——这个数能不能被写回去驱动仿真，还是只读快照？
  5. state-transfer success（状态迁移成功）——把 A 的状态写进 B，B 真的接受并复现了吗？
  6. trajectory parity（轨迹一致）——给同样的动作，两边的轨迹真的吻合吗？
  7. task success（任务成败）——最终任务做成了吗？

下面这个部件把第 2 条演给你看：两个 shape 一模一样的张量，仅仅因为 joint ordering 不同，逐元素相减就得出一个看似精确、实则胡说的「差异」。这正是 stage50 bug 的种子。

interactive同形状、不同 joint ordering，为什么不可比
两个张量 shape 相同，按 index 对齐相减得到「差异」；切换到 by-name 对齐才看到真相。形状对齐 ≠ 语义对齐。

MetaSim 的 TensorState：对的工具，错的用途

这里要非常公平地对待 MetaSim / RoboVerse（arXiv:2504.18904）。它的 TensorState 是一个优秀的设计——但优秀在一个和 EOS 不同的目标上。MetaSim 的每个仿真器有一个 Handler（MujocoHandler、IsaacLabHandler、PybulletHandler 等），通过 get_state(mode='tensor') 吐出 TensorState：它把 DoF / body 按 lexicographical order（字典序）组织，分组成 objects / robots / cameras。对于执行人机工程——批量 rollout、喂进 GPU、跨 sim 共用一套训练循环——这种规整的张量布局非常顺手。

问题不在 TensorState 本身，而在把它当评测真相。字典序是一种机械的、与场景无关的排序：它保证「同一个 handler 内部稳定」，但不保证「跨后端语义对齐」。两个后端各自按字典序排，第 k 个 DoF 在语义上可能根本不是同一个关节。EOS 要做的是跨后端比较结论，所以它需要的不是字典序，而是一张场景拥有的 semantic component map（语义组件映射）——由 scenario pack 声明「哪个语义部件对应哪个后端实体」，比较才在语义上成立。这正是招牌对照句要分清的两件事：

招牌对照句

“MetaSim solves cross-simulator execution ergonomics; EOS solves evidence-backed embodied evaluation claims.”

从物理后端 看 字典序张量为何在跨引擎时失真

MetaSim 的 Handler 生命周期是 launch / get_state / set_state / simulate / close，外加 get_joint_names / get_body_names——注意后两个方法的存在本身就承认了：名字是真相，顺序只是布局。一旦你跨引擎（MuJoCo vs PyBullet vs Genesis）比较，接触是个 NCP（非线性互补问题），各引擎为速度与稳定性各自松弛（线性化摩擦锥、软化互补）。所以同一个动作下，连「力」都分裂成接触求解力、约束保持力、源引擎特有的保持力等不同力家族——SimBenchmark、cloth-manipulation benchmark 都实测过 dynamic 场景没有引擎能精确互相匹配。一个按字典序拼出来的张量，把这些语义差异碾平成了同一个 shape 的相邻浮点数。EOS 拒绝在这种碾平之上做减法。

Gym 式 obs→action→reward→done 只是 adapter 便利

同样的逻辑也适用于另一个诱惑：Gym 那套 obs → action → reward → done 的接口。它当然好用——整个 RL 生态都建在上面。但在 EOS 里，它只是adapter 层的便利，不是评测真相的形状。一个 reward 标量和一个 done 布尔，把上一节那条挂着 L4 物理投影、L5 语义状态、provenance、claim boundary 的 TraceStep 压成了两个数——它丢掉了「这一步发生了什么、归谁所有、能证明什么」的全部信息。所以 EOS 允许 adapter 在边界上呈现 Gym 形状（方便接入现有模型），但内部的证据始终是 EpisodeTrace，不是 (obs, reward, done) 元组。

从评测科学 看 把张量当真相，就是 construct 被 measurement 顶替

这正是 0.1 提过的 construct validity 问题在状态层的复现。Raji 等人（NeurIPS 2021）警告过「Everything in the Whole Wide World Benchmark」式的错觉：用一个号称通用的量度，假装测到了普适能力。一个裸 TensorState 上的逐元素差，就是把「测量量（两个浮点数组的距离）」直接冒充成「构念（两个后端是否在做同一件事）」。EOS 的三层状态 + semantic component map，正是拒绝这种顶替——它坚持让场景来定义「同一件事」是什么，再谈比较。

这一节带走的

三件事：（1）同形状证明不了任何东西——它对 component inventory、ordering、frames/units/sign/force families、writability、transfer success、trajectory parity、task success 全都沉默；（2）MetaSim 的 TensorState（字典序、分组 objects/robots/cameras）是优秀的执行人机工程工具，但 EOS 跨后端比较需要的是场景拥有的 semantic component map，而非机械字典序；（3）Gym 的 obs→action→reward→done 只是 adapter 便利，EOS 内部的证据永远是 EpisodeTrace。

这一部分的总边界

把整个 Part 3 收成一句 claim boundary：EOS 的脊柱证明的是它有能力诚实地谈论跨后端、跨场景的评测——把每一份证据归位、标注出处、声明边界、定位差异。它不证明、也从不打算用结构本身去证明：backend parity、trajectory parity、contact / force-vector parity、official benchmark reproduction、hardware readiness、real-world safety。这些词属于 Forbidden Claim Catalog，没有配套证据一律不许用。结构让你能够诚实，但诚实仍要靠每一次评测去挣——而那，就是接下来几部分的事。
