三层状态：measure → project → semantics

上一节我们说 L0–L6 脊柱的中段——L3、L4、L5——是「状态」被拆成的三层。这一节把这三层钉死在代码上：它们各自是哪个 dataclass、装哪些字段、由谁产生、给谁看。你会看到一个原始的 qpos 向量如何走完「measure → project → semantics」这条流水线，最后变成场景才认得的 finger_cap_contact。核心问题只有一个：为什么必须是三层，而不能省成一层。

三种状态，三个 dataclass

EOS 的状态不是一个对象，而是三个：每一个对应脊柱上的一层，住在 core/state/world_state.py（语义/投影）和 runtime（原始测量）里。先把三者的身份摆清楚：

  • L3 · RuntimeMeasurementSnapshot——raw / measured。后端测出来或导出来的东西，artifact-backed、immutable、capability-scoped。它不保证完整、不保证可恢复、不保证可独立比较。它是证据的原料，还带着后端方言（native alias）。
  • L4 · PhysicalStateProjection——projected / simulator-neutral。把 L3 归一化成「不带后端口音」的物理投影，让跨后端比较有共同语言。
  • L5 · TaskSemanticState——semantics。场景拥有的语义/过程状态，core 不认得里面的字段名，只存 schema-validated 的 payload。

下面这个部件把这条流水线演出来：一个原始 qpos 向量从 L3 进来，经 L4 投影成 simulator-neutral 字段，再被场景原语解读成 finger_cap_contact 这样的语义事实。

L4 PhysicalStateProjection：simulator-neutral 的字段表

L4 是三层里最值得逐字看的，因为它定义了「跨后端可比」到底长什么样。看 core/state/world_state.py 里真实的 dataclass：

src/embodied_eval_os/core/state/world_state.py
@dataclass
class PhysicalStateProjection:
    """Backend-normalized physical evidence derived from L3 measurement.

    Examples: object poses, robot joints, velocities, contacts, sensor states.
    """

    time_s: float
    objects: dict[str, Any] = field(default_factory=dict)
    robots: dict[str, Any] = field(default_factory=dict)
    joints: dict[str, Any] = field(default_factory=dict)
    contacts: list[dict[str, Any]] = field(default_factory=list)
    metadata: dict[str, Any] = field(default_factory=dict)

它的字段都是结构化的、场景中立的物理量：time_s 是这一帧的时间；robots 里典型装 qpos / qvel / ee_pose；objects 里每个物体装 pose / velocity；joints 里每个关节装 q / qd；contacts 是一串 {body_a, body_b, normal_force}。

注意 qpos 在这里是「字段值」，不是 core API 名

你也许记得 qpos / qvel 是 core 禁词表里的名字——leakage checker 会因为 core 代码里出现这两个 token 而报红。这里没有矛盾：禁的是把 qpos 当成 core 的命名/API（比如一个 CanonicalRobotState.qpos 属性）。而在 L4 投影里，robots 是一个 dict[str, Any]，qpos 只是某个后端投影时往字典里塞的一个键——它是数据，不是 core 的符号。core 代码本身从不写出这个名字。

L5 TaskSemanticState：场景拥有的语义

L5 是场景的地盘。它的 dataclass 同样在 world_state.py 里：

src/embodied_eval_os/core/state/world_state.py
@dataclass
class TaskSemanticState:
    """Evaluator-visible scenario/process semantics.

    Scenario-specific process/domain state.
    Core does not assume any one scenario, setting, simulator, or benchmark.
    """

    process_state: dict[str, Any] = field(default_factory=dict)
    hazard_events: list[dict[str, Any]] = field(default_factory=list)
    procedure_state: dict[str, Any] = field(default_factory=dict)
    metadata: dict[str, Any] = field(default_factory=dict)

三个语义槽：process_state（过程到了哪一步）、hazard_events（发生了哪些危险事件）、procedure_state（流程/SOP 状态）。关键在那句 docstring：「Core does not assume any one scenario, setting, simulator, or benchmark.」 core 给的是三个空字典/列表的形状，里面装什么由 scenario pack 决定。finger_cap_contact、spillage、protocol_step 这些字段名，core 一个都不认得——它只负责存 schema 校验过的 payload。

还有一条硬约束写进了代码：L5 不许内嵌 L4。trace.py 在反序列化时会显式拒绝把 physical_state_projection 塞进 TaskSemanticState：

src/embodied_eval_os/core/state/trace.py
INVALID_TASK_SEMANTIC_KEYS = {
    "physical_state_projection",
}
# ...
invalid_keys = INVALID_TASK_SEMANTIC_KEYS.intersection(payload)
if invalid_keys:
    raise ValueError(
        "TaskSemanticState cannot embed physical_state_projection; "
        "put L4 physical evidence on TraceStep.physical_state_projection"
    )

这条 guard 不是洁癖，而是分层的执法：L4 的物理证据必须挂在 TraceStep.physical_state_projection 上，而不能藏进 L5 的语义里。否则「物理真相」和「场景解读」就又搅成一坨了——正是上一节我们费力分开的那种坨。

为什么是三层，不是一层

把这三层压成一个「world state」对象，省下来的代码量，会以三种代价偿还回来：

  1. 跨后端可比性会丢。L3 带着后端方言（MuJoCo 的 native dump 和 PhysX 的不是一回事）。如果不先经 L4 归一化就拿去比较，你比的是方言而不是物理。L4 这一层存在的唯一理由，就是给跨后端比较一个 simulator-neutral 的共同语。
  2. 证据边界会塌。L3 明确不保证完整或可恢复——它只是「这个后端这次能测到/导出的东西」。把它和「保证可比的投影」混为一谈，等于偷偷把一个弱证据当强证据用。三层让「测到了什么」和「归一化出了什么」各自诚实。
  3. core 会被场景污染。L5 的字段名属于场景。如果语义直接长在物理状态对象上，core 就不得不认得 finger_cap_contact 之类的名字——铁律一当场失守。三层把场景语义关在 L5 的 dict 里，core 只见 schema，不见场景。
从评测科学 看 三层就是 measurement → operationalization → construct

测量科学里，从「仪器读数」到「你声称测到的构念」之间从来不是一步。L3 是 raw measurement（仪器读到的数）；L4 是把它归一化成可比的 operationalization（你定义的、跨设置一致的量）；L5 才是 construct（你真正想谈的语义事实，比如「夹爪接触到了瓶盖」）。把三者压成一层，正是 Jacobs & Wallach（FAccT 2021）说的 operationalization gap 的温床——你以为在谈构念，其实手里只有方言读数。EOS 把这段距离显式切成三层，每一跳都留下可审计的痕迹。

State V2：改名不是洁癖，是迁移硬重构

这三层名字是 State V2 重构后的结果。早期 V1 用的是另一套名字，V2 做了一次硬改名，并把 V1 的读取路径全部赶进 tools/migrations/state_v1/。对照表值得记住：

State V1 → V2 改名表
CanonicalPhysicalState        → PhysicalStateProjection
TaskWorldState                → TaskSemanticState
canonical_physical_state      → physical_state_projection
task_world_state              → task_semantic_state
world_state / metrics alias   → 从主 API 删除
get_canonical_state()         → measure() + project_physical_state(...)

最后一行最能说明 V2 的精神：旧的 get_canonical_state() 一步到位地「拿当前状态」，悄悄把 measure 和 project 两件事糊在一起。V2 把它拆成 measure()（拿 L3 原始测量）+ project_physical_state(...)（归一化成 L4）两个显式步骤——流水线的每一跳都被命名、被看见。

而且这套改名是带牙齿的：上一节提过、下一节会细看的 TraceStep.from_dict，会主动检测 canonical_physical_state、task_world_state 这些 legacy key 并直接报错，把你指向迁移模块。换句话说，你不可能把一条 V1 的 trace 当 V2 喂进来还蒙混过关。

三层状态证明了什么 · 不证明什么

三层状态证明的是：每一帧的物理证据，从原始测量到场景语义，走过了一条显式的、各层归属清楚的归一化路径——所以你能诚实地说「这个语义事实是从哪个后端的哪个测量、经哪一步投影得来的」。它不证明 L4 的投影在物理上「忠实」于真实世界，也不证明两个后端的 L4 数值可以直接相等比较——那需要 L6 的 provenance 和成对诊断来支撑。投影让差异可定位，不让差异消失。

这一节带走的

三件事：（1）EOS 的状态是三个 dataclass——L3 RuntimeMeasurementSnapshot（raw）、L4 PhysicalStateProjection（simulator-neutral，字段 time_s/robots/objects/joints/contacts）、L5 TaskSemanticState（场景语义 process_state/hazard_events/procedure_state）；（2）必须三层，因为压成一层会同时丢掉跨后端可比性、塌掉证据边界、污染 core；（3）这套名字是 State V2 改名的产物，迁移带牙齿——legacy key 会被 from_dict 当场拒绝。
