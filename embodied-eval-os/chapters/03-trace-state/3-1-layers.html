L0–L6 分层：从资源到证据账本

前两部分你把 EOS 的身份（高一层的评测 OS）和它的后端组合学（六个可替换组件）摸清楚了。但有一个问题被刻意推迟到了这里：当一台仿真器真的跑起来、世界每一步都在变，这些「状态」到底住在哪、归谁所有、谁有资格把它当成证据？EOS 给出的答案是一条七层的脊柱——L0 到 L6，从一块静态资源，一路走到可审计的证据账本。这一节先把这根脊柱立起来。

为什么要分层，而不是一坨「world state」

一个自然但危险的想法是：让仿真器直接吐出一个「当前世界状态」，评测器拿去打分就完事了。这正是大多数 benchmark 的做法，也正是 EOS 拒绝的做法。原因是：当你想跨后端比较时，「世界状态」这个词会在不知不觉间偷换三件互相独立的东西——它是谁拥有的、它用什么格式装载、它背后的真相由谁产生。把它们混成一坨，结论就站不住。

EOS 的处理方式是把整条从「资源」到「证据」的路径切成七层，每一层只负责一件事，并且明确归属——哪些在 core/，哪些在 runtime/，哪些归 scenario pack。下面这个探索器，你可以逐层点开看每一层的职责与归属：

从 EBench 看 你已经见过这根脊柱的「散装版」

EBench 教程第 8 章拆过一个评测系统的解剖：Spec（任务规格）→ State（环境状态）→ Runtime（执行引擎）→ Metric（打分）→ Report（报告）。那是一套很好的直觉骨架。EOS 做的事，就是把这套散装直觉焊成一条带编号、带归属的脊柱：EBench 的 Spec 对应 L1 EvaluationWorldSpec，Runtime 对应 L2 WorldSession，State 被拆成 L3/L4/L5 三层（下一节专门讲），Metric+Report 沉淀进 L6 Evidence Ledger。同一套直觉，换上可审计的编号。

七层，逐层看

从下往上，每一层都建在前一层之上，但只暴露自己该暴露的东西：

  • L0 Resource / Asset——最底下的静态原料：网格、URDF/MJCF 文件、纹理、材质。它还不是一个「世界」，只是世界的零件。
  • L1 EvaluationWorldSpec——对「要评测的那个世界」的声明式规格：放哪些资产、初始分布、观测/动作规格。它是意图，还没跑起来。
  • L2 WorldSession——live runtime 的会话信封：lifecycle、clock、domain channels、control、sensors、native artifact refs、capability 声明。这是「世界真的在跑」的那一层。
  • L3 RuntimeMeasurementSnapshot——从 L2 测量/导出出来的跨后端证据边界：immutable、artifact-backed、capability-scoped。
  • L4 PhysicalStateProjection——把 L3 的原始测量归一化成 simulator-neutral 的物理投影。
  • L5 TaskSemanticState——场景拥有的语义层：process / procedure / hazard / evaluator 字段。
  • L6 Evidence Ledger / EpisodeTrace——把上面一切沉淀成可审计的证据账本，也就是 3.3 要解剖的 EpisodeTrace。

L3 → L4 → L5 这三层是「归一化三步」：raw/measured → simulator-neutral → 场景语义，下一节 3.2 会逐字对照代码讲清楚。这一节先把更隐蔽、也更容易被问错的东西讲透——L2 到底是什么。

三轴解耦：别问「USD 是不是那个活的世界」

EOS 架构记录里（l2-l3-layering-clarification）有一个堪称定海神针的洞察：很多关于「状态住在哪」的争论，其实是把三条互相正交的轴搅在了一起。把它们分开，问题就消解了：

  1. layer ownership（层归属）——L0–L6，谁拥有这层语义。这是组织问题。
  2. interchange format（交换格式）——USD 还是 MJCF？这是装载格式问题。
  3. runtime truth（运行时真相）——MuJoCo / Genesis / PhysX / 真实世界，谁产生了这一步的物理真相。这是真相来源问题。

一旦三轴分开，「USD 是不是那个活的世界？」就立刻显出它是个错问题：USD 只是一种 interchange format（轴二），它既不决定层归属（轴一），也不决定谁产生了运行时真相（轴三）。你完全可以用 USD 描述一个由 MuJoCo 产生真相的世界，也可以用 MJCF 描述一个由 PhysX 跑的世界。问「USD 是不是活的」，等于把格式问题误当成真相问题。

从物理后端 看 同一个 task，三引擎三个真相

把三轴摆开，跨引擎差异就有了正确的坐标系。同一个 L1 EvaluationWorldSpec（轴一固定）、可以用同一份 USD 资产（轴二固定），但在 MuJoCo 上跑和在 Genesis 上跑（轴三不同），接触求解、穿透、稳定化各不相同——这是真实的、有据可查的引擎差异（SimBenchmark、cloth-manipulation benchmark 都量过：quasi-static 大家都准，dynamic 没有引擎能精确互相匹配）。EOS 的北极星因此是：「在同一套 task 与证据规则下，不同 physics 后端产生的结果，可以被测量、投影、比较、审计，而不过度宣称。」 三轴解耦正是让这句话可执行的前提。

L2 WorldSession：USD-covering，不是 USD-shaped

L2 WorldSession 是这根脊柱上最容易被误解的一环，值得单独说清三件事。

第一，它是会话信封，不是世界本体。WorldSession 持有的是 lifecycle、clock、domain channels、control、sensors、对 native artifact 的引用、以及这个后端宣称的 capability。它不是 USD 场景的克隆，也不是逐步状态（per-step state）的拥有者——逐步的物理证据归 L3/L4，语义归 L5。

第二，它「USD-covering，不是 USD-shaped」。这句话的意思是：WorldSession 的接口要能覆盖一个 USD 级别世界所需的能力（生命周期、时钟、控制、传感、原生产物引用），但它的形状不由 USD 的数据模型决定。它不是「USD 的一个薄包装」；一个完全不用 USD 的后端（比如纯 MJCF 的 MuJoCo provider）一样能填满这个信封。把接口绑死到 USD 的形状，等于让一种 interchange format 反塑了 core——这正是 铁律二禁止的事。

第三，它住在 runtime/，不在 core。这是个有意的归属决定：core 只关心契约（L1 的规格、L4 的投影 schema、L5 的语义 payload、L6 的证据结构）。「世界正在某个具体后端上活着」这件事是 runtime 的职责，所以 WorldSession 的代码落在 src/embodied_eval_os/runtime/。这样 core 就永远不必知道任何一个具体仿真器是怎么管理它的会话的。

这套分层证明了什么 · 不证明什么

L0–L6 分层证明的是：EOS 有能力把「资源 / 规格 / 会话 / 测量 / 投影 / 语义 / 证据」这七件事各自归位、各自可审计，从而让跨后端比较有一个干净的坐标系。它不证明任何两个后端的物理是等价的——分层只是让差异可被定位到某一层、某一轴，差异本身仍是证据（见 7.2 的 first-divergence 诊断），而不是 parity claim。一句话：分层让你能诚实地说「它们在 L4 的 contact_force 上分叉」，但它从不让你说「它们一样」。

这一节带走的

三件事：（1）EOS 把从资源到证据的路径切成 L0–L6 七层，每层只管一件事、且明确归属——L2 在 runtime，L4/L5/L6 的 schema 才是 core 的契约；（2）三轴解耦——layer ownership / interchange format / runtime truth 互相正交，所以「USD 是不是活的世界」是个错问题；（3）L2 WorldSession 是会话信封，「USD-covering 而非 USD-shaped」，不拥有逐步状态、也不让任何格式反塑 core。
